M2B — Map byte

M2B is the dense, PID-indexed backing store for M2. Where M2 accepts arbitrary keys and stores values in a Map, M2B stores fixed-width values in a flat Float64Array, indexed by integer PID. pidToSlot / slotToPid give O(1) lookup in both directions, and iteration walks the dense slot range — no hashing, no per-entry allocation.

stride controls how many doubles each PID holds: stride = 1 stores scalars (number), stride > 1 stores fixed-length Float64Array views. cap is the maximum PID; values outside [0, cap) read as absent.

M2BIN — Binary Map

M2BIN is a binary-backed map implementation optimized for numeric keys and numeric values. It uses typed arrays and direct PID-to-slot indexing for its fast path, while retaining a native Map as a fallback for other key/value combinations.

Numeric keys are treated as PIDs. Values are stored in a Float64Array, with Int32Array indexes mapping PIDs to dense storage slots and slots back to PIDs. Deletion uses swap-with-last compaction, keeping the dense storage packed without leaving gaps.

The backing arrays grow automatically when a PID or dense slot exceeds the current capacity. Growth doubles the capacity and copies the existing typed-array contents into the expanded buffers.

Intended use

M2BIN is intended for workloads where:

  • Keys are numeric PIDs.
  • Values are numeric.
  • Fast direct reads and writes are important.
  • Dense iteration is preferable to sparse PID-indexed storage.
  • Bulk numeric reads benefit from typed-array operations.
  • Non-binary entries still need a fallback storage path.

M2D — Dense Map

M2D is a dense, PID-indexed map implementation backed by typed arrays. Numeric keys are used directly as array indexes, eliminating the PID-to-slot indirection used by M2BIN.

Values are stored at their corresponding PID positions in a Float64Array. A parallel Uint8Array tracks whether each position is occupied. This provides constant-time direct access while allowing sparse PID ranges without treating uninitialized positions as existing entries.

A secondary M2 instance provides fallback storage for entries that do not qualify for the numeric binary path.

When a numeric PID exceeds the current capacity, the backing arrays grow automatically. Capacity doubles until the requested PID fits.

Dense iteration

Intended use

M2D is intended for workloads where:

  • Numeric PIDs are the primary keys.
  • Values are numeric.
  • Direct PID-to-array-index access is desirable.
  • Dense iteration over occupied positions is important.
  • Typed-array operations and bulk reads are useful.
  • A fallback map is still needed for non-binary entries.

M2R — Row Map

M2R is a binary-backed map designed for storing fixed-width numeric rows under numeric PIDs. It combines dense slot storage with direct PID-to-slot indexing, allowing rows to be stored contiguously while supporting sparse PID values.

Each entry occupies a fixed-width row in a Float64Array. The configured stride determines the number of numeric components per row. A pair of Int32Array indexes maps PIDs to dense slots and slots back to PIDs.

Unlike M2D, which stores one numeric value directly at each PID index, M2R stores complete rows in packed storage. Deletion uses swap-with-last compaction, keeping the active rows contiguous.

Capacity and growth

The constructor accepts an initial PID capacity and row stride:

new M2R<K>(1024, 3)

The default stride is 3.

When a PID or dense slot exceeds the current capacity, the index arrays and value buffer grow automatically. Existing mappings and row data are preserved.

Deletion and compaction

Deleting a row moves the final active row into the deleted row's slot when necessary. The PID mappings are updated accordingly, keeping active storage contiguous.

Consequently, dense slot positions are not stable across deletions. Use slotOf(pid) whenever the current slot is needed.

Intended use

M2R is intended for workloads where:

  • Numeric PIDs identify records.
  • Each record contains a fixed number of numeric components.
  • Contiguous row storage is preferable to individually allocated objects.
  • Direct component access is important.
  • Dense iteration and bulk buffer access are useful.
  • Zero-copy row views are desirable.

Experimental Map Implementation

Personally, I think this is pretty cool... but who knows, it might be absolute shit, haha.

This implementation is intended for anything other than nested map configurations. I've found that particular workload simply doesn't bode well for disruptors. I've tried rebuilding the nested map function as a disruptor more times than I care to count, and I haven't managed to get it to perform better than the original. At that point, there's simply no reason to keep pursuing it.

This implementation takes a different approach. The idea is to provide a more performant alternative to Map, while keeping the operations as close to native Map functions as possible. The less overhead introduced by the disruptor itself, the better.

There are two planned versions:

  • MDisruptor — The conventional implementation, using sequence numbers to track ring positions and manage slot ownership. It uses an index to locate entries and a circular buffer to hold their payloads.
  • M2Tracer — A variation that replaces wall-clock epochs with what I call a tracer particle. Rather than maintaining a centralized clock somewhere inside the class, each key-value pair carries its own clock value directly in the ring.

The Tracer Particle

The idea is surprisingly simple: every time a particle completes a revolution around the ring, its counter increments.

Instead of relying on timestamps, expiration is measured in revolutions. This gives us a clock that advances alongside the actual workload rather than independently of it.

The benefits of this approach extend well beyond simply replacing an epoch:

  • Free backpressure: The ring's own progression provides a natural mechanism for managing data lifetime.
  • Revolution-based TTL: Entries expire according to actual ring activity rather than elapsed wall time.
  • No stale data accumulation: Data cannot remain valid indefinitely simply because an external clock hasn't triggered cleanup.
  • No background expiration work: There is no need for timers or periodic sweeps to keep the data current.
  • Per-entry timekeeping: Each particle carries its own clock, eliminating the need for a centralized expiration clock.
  • Workload-driven expiration: Idle systems don't need to wake up just to advance expiration timers.

The particularly interesting part is that the clock isn't an additional mechanism running alongside the data structure. It is part of the data structure itself.

Implementation

Both implementations are intentionally kept extremely small. In fact, the conventional implementation is among the smallest map implementations in this library.

MDisruptor uses two primary structures:

Structure Responsibility
Disruptor Circular buffer holding sequenced key-value slots
index Native Map providing direct key-to-sequence lookup

The ring uses power-of-two capacity and bitwise masking for slot addressing. Each slot carries its sequence number, key, payload, and tombstone state.

A few implementation details are worth highlighting:

  • Evict-and-carry: Before claiming a ring slot, a still-live occupant is relocated forward and its index updated. This prevents live entries from being silently overwritten during ring wraparound.
  • Lazy deletion: Deleting an entry removes its index reference without immediately modifying the ring. The old slot can be reclaimed when it is encountered again.
  • Automatic growth: Capacity increases when the indexed entry count reaches the configured occupancy threshold.
  • Value isolation: Values are encoded on insertion and decoded on retrieval, using structuredClone when available and a JSON fallback otherwise.
  • Function rejection: Functions cannot be stored as state values. This implementation is intended for data, not executable behavior.

The Bigger Idea

The interesting part here isn't simply putting a Map on top of a disruptor.

It's finding ways to make the underlying transport do more of the work that would otherwise require additional machinery. The tracer particle is a particularly good example: a tiny addition to each entry potentially eliminates an entire category of centralized timekeeping and expiration overhead.

That's the direction I'm exploring with this implementation. Keep the hot path small, keep the operations familiar, and let the ring do the heavy lifting.

MTracer — Tracer Particle Map

MTracer is the second implementation of M2Disruptor. Rather than relying on a conventional epoch or wall-clock timestamps, it uses a revolution-based clock that advances with the ring itself.

The central idea is the tracer particle: every entry is assigned to a lane, and each lane represents a position in a rolling time window. As entries are written, the active lane fills. Once full, the dial advances to the next lane. Completing a full rotation increments the revolution counter.

There is no Date.now(), no interval, no background timer, and no periodic cleanup process.

Architecture

The implementation consists of three primary structures:

Structure Responsibility
Disruptor Circular buffer with sequence-based slot addressing
Lane Manages a ring, tracks write capacity, and reports pressure
index Native Map providing direct key-to-lane and sequence lookup

The MTracer itself coordinates the lanes through a rotating dial.

By default, it uses seven lanes, each with a capacity of 256 entries. This creates a rolling seven-lane window, with each completed rotation advancing the revolution counter.

The Tracer Particle

The tracer particle is the clock.

public revolution = 0;

Every time the dial completes a full rotation, the revolution counter increments.

Each entry is associated with its lane and sequence number:

interface IndexEntry {
    lane: number;
    seq: number;
}

This means expiration is implicit in the lifecycle of the lane containing the entry.

When the dial returns to a previously occupied lane, that lane is reset. Its previous ring is replaced entirely, and index entries still pointing to that lane are removed.

The old ring is no longer referenced and becomes eligible for garbage collection.

No individual entries need to be traversed, tombstoned, or explicitly expired inside the ring.

Lane Rotation

The lifecycle is straightforward:

  1. Writes enter the currently active lane.
  2. Each write advances that lane's write counter.
  3. Once the lane reaches capacity, the dial advances.
  4. Completing a full rotation increments revolution.
  5. The lane being revisited is reset and its remaining index references are discarded.

This produces a rolling expiration window without requiring an independent expiration mechanism.

Backpressure

One particularly interesting property is that pressure comes directly from lane utilization.

Property Description
isFull Whether the active lane has reached capacity
pressure Active lane utilization, from 0 to 1
revolution Number of completed dial rotations
dial Current active lane

The pressure getter provides an immediate indication of how close the active lane is to triggering a rotation.

get pressure(): number {
    return this.activeLane.pressure;
}

There is no separate queue-depth tracker or instrumentation required. The structure already knows how much work has entered its active lane.

Like MDisruptor, values pass through encode and decode.

Why This Is Interesting

The difference between a conventional epoch and a tracer particle might seem small, but the architectural implications are significant.

Traditional expiration mechanisms require a separate concept of time. They need timestamps, comparisons, cleanup operations, and often some mechanism to periodically wake up and perform that work.

MTracer takes a different approach.

Time advances because the data structure is being used.

The lanes already know when they are full. The dial already knows when to advance. The revolution counter already knows when a complete cycle has occurred. Expiration becomes a consequence of ring rotation rather than a separate operation.

Some of the resulting properties:

  • No wall-clock dependency: Expiration is entirely independent of system time.
  • No background work: Nothing needs to wake up to advance the clock.
  • Automatic reclamation: Old lanes are replaced wholesale rather than cleaned entry by entry.
  • Bounded lane storage: Each lane has a fixed capacity.
  • Natural pressure reporting: Lane utilization provides an immediate pressure measurement.
  • Simple lifecycle: Rotation and reset handle the expiration of entire generations of entries.

The seven-lane configuration is simply the default. Both lane capacity and dial size are configurable.

The tracer particle is a small idea, but it changes how expiration is approached entirely. Instead of maintaining a clock alongside the data structure, the data structure becomes its own clock.

barrier

Wait for N things to happen. No counters. No mutexes. No race conditions.

A minimal, single-file barrier primitive for TypeScript and JavaScript. Create a barrier with a count, call .arrive() from anywhere that needs to check in, and await .wait() to unblock once every arrival has happened. That's the whole API.

This is the correct way to express "wait until N things have happened" — a pattern that shows up in distributed systems, parallel test runners, rasterizers finishing tile batches, peer coordination, and every Promise.all-adjacent problem you've ever hand-rolled. Most implementations invent a shared counter, a mutex, and a condition variable and still get the race condition wrong. This one doesn't, because it has none of those things.

Usage

🟢 First-time users — start here

The absolute minimum to get this working in under 5 minutes:

import { barrier } from "barrier"

const b = barrier(3)

b.arrive()  // 1st
b.arrive()  // 2nd
b.arrive()  // 3rd — this one resolves the wait

await b.wait()  // resolves after the 3rd arrive()

That's it. You're done. You now know how to use barrier.

If you want it to actually be useful, here's the same thing with real async work:

import { barrier } from "barrier"

const ready = barrier(3)

async function worker(id: number) {
  await doSomeSetup()
  ready.arrive()
  await ready.wait()
  console.log(`worker ${id} proceeding`)
}

await Promise.all([worker(1), worker(2), worker(3)])

Every worker blocks until all three have checked in. No counter. No mutex.

🔵 Everyone else — the full picture

The API

function barrier(n: number): {
  arrive(): void
  wait(): Promise<void>
}
  • barrier(n) — creates a barrier that resolves once n callers have called .arrive().
  • .arrive() — records one arrival. When the n-th arrival happens, the internal promise resolves. Idempotent in the sense that extra arrivals past n are harmless no-ops.
  • .wait() — returns the same promise every time. Safe to call before, during, or after all arrivals. Safe to call from many places. Returns immediately (on the next microtask) if the barrier is already resolved.

Why wait() returns the same promise

wait() is not a one-shot. It's not a consumable. It can be awaited by every participant independently, and by anyone else who happens to hold a reference. This is what makes the primitive composable — you can hand the barrier object to N workers, or to a coordinator, or to both.

n is captured at construction

The count is fixed when you call barrier(n). This is deliberate. A barrier whose target can change underneath waiting callers is a barrier that has to be locked, and the moment you lock it you've reinvented the thing this exists to avoid.

Arrivals are counted synchronously

arrive() is not async and does not yield. It increments and, if the threshold is met, resolves. This means:

  • Two .arrive() calls in the same synchronous tick are counted correctly.
  • You cannot lose an arrival between the increment and the check.
  • There is no window for a race.

The gate dependency

Internally this uses a gate<void>() helper that returns { promise, resolve }. If you're vendoring the code, gate is a two-liner:

function gate<T>() {
  let resolve!: (v: T) => void
  const promise = new Promise<T>(r => { resolve = r })
  return { promise, resolve }
}

Common patterns

Wait for N peers to check in

const allHere = barrier(peerCount)
peers.forEach(p => p.on("ready", () => allHere.arrive()))
await allHere.wait()

Parallel test runner — wait for N suites to finish setup

const setupDone = barrier(suites.length)
await Promise.all(suites.map(s => s.setup().then(() => setupDone.arrive())))
await setupDone.wait()

Rasterizer — wait for N tiles

const done = barrier(tiles.length)
for (const tile of tiles) {
  renderTile(tile, () => done.arrive())
}
await done.wait()

What this is not

  • Not reusable. Once resolved, it stays resolved. If you need a cyclic barrier (reusable across rounds), that's a different primitive and you should build it on top of this one, not inside it.
  • Not a Semaphore. It doesn't track available permits or block on acquisition. It only counts arrivals toward a single threshold.
  • Not a Latch in the Java sense, although it's close. A latch typically supports count-down semantics; a barrier is symmetric — all parties arrive and then all parties proceed.

Gotchas

  • Calling .arrive() more than n times is fine but the extra calls do nothing. If you find yourself arriving more than you expected, you have a bug elsewhere and this primitive will not hide it from you.
  • .wait() never rejects. It has no timeout, no abort signal, no cancellation. If you need those, wrap it: await Promise.race([b.wait(), timeout(5000)]).
  • Zero is a valid n — barrier(0).wait() resolves immediately. This is useful as a fallback in code where the participant count is dynamic.

Philosophy

Every "wait until N things happen" you've ever written by hand has had a shared counter and a resolve call and a check, and every one of them had a subtle bug the first time. This is the smallest correct expression of that pattern. Use it instead of the counter.

callIf

Call a function only if a condition is truthy. Return the result, or undefined. That's the whole thing.

A tiny utility for the extremely common pattern of "evaluate this expression only if this other thing is true." Instead of writing cond ? fn() : undefined inline — which is fine but noisy, gets nested badly, and evaluates the condition twice if you're not careful — you write callIf(cond, fn). It's the smallest possible ternary helper, and it composes.

Usage

🟢 First-time users — start here

The absolute minimum to get this working in under 5 minutes:

import { callIf } from "call-if"

callIf(true,  () => "yes")   // "yes"
callIf(false, () => "yes")   // undefined
callIf(0,     () => "yes")   // undefined (falsy)
callIf("x",   () => "yes")   // "yes"   (truthy)

That's it. You're done. You now know how to use callIf.

If you want the real-world version, here it is:

import { callIf } from "call-if"

const user = getUser()
const greeting = callIf(user?.isActive, () => `Welcome back, ${user.name}!`)

When the user is active, you get the greeting. When they're not, you get undefined and never touch user.name — which matters if user is null.

🔵 Everyone else — the full picture

The API

function callIf<T>(condition: any, fn: () => T): T | undefined
  • condition — any value. Evaluated for truthiness with standard JS semantics (false, 0, "", null, undefined, NaN are falsy; everything else is truthy). Typed as any on purpose so you can pass optional chains, boolean expressions, nullable values, whatever — without fighting the compiler.
  • fn — a thunk. A zero-argument function that computes the value. It is only invoked if condition is truthy.
  • Returns — the result of fn() if condition is truthy, otherwise undefined. The return type is T | undefined.

Why a thunk, not a value

You pass () => computeTheThing(), not computeTheThing(). This is the entire point. The function body is never evaluated unless the condition passes. If you pass a value, you've already paid the cost — including any side effects, null derefs, or expensive computation — before callIf even runs.

// ✅ lazy — fn() only runs when user is non-null
callIf(user, () => user.name)

// ❌ eager — this throws before callIf sees it
callIf(user, user.name)  // not even valid; user.name evaluated up front

Narrowing doesn't happen — plan for it

TypeScript cannot narrow types through callIf. The signature takes condition: any and returns T | undefined, so the compiler does not know that inside fn, the condition was true. If you need narrowing, do it yourself:

callIf(user, () => {
  // user is still `User | null` here as far as TS is concerned
  return user!.name
})

For cases where narrowing matters more than terseness, a plain if is still the right tool. callIf is for when the result is the point, not the narrowing.

Comparisons

// Ternary
cond ? fn() : undefined

// Boolean AND
cond && fn()   // ← returns `false` / `0` / `""` when cond is falsy, not `undefined`

// callIf
callIf(cond, fn)

The difference between callIf and && is the falsy return value. false && x() gives you false; callIf(false, x) gives you undefined. When you're building an object or JSON payload, undefined disappears during serialization while false does not. That difference bites people in real code.

const payload = {
  name: user.name,
  nickname: callIf(user.hasNickname, () => user.nickname),
}
// JSON.stringify drops `nickname` entirely when the condition is false.
// With `&&` you'd get `"nickname": false` in your payload. Oops.

Common patterns

Optional fields in an object literal

const options = {
  retries: callIf(config.retries, () => config.retries),
  timeout: callIf(config.timeout, () => config.timeout),
}

Conditional rendering in a React-ish render function

{callIf(user.isAdmin, () => <AdminPanel />)}

Guard against null deref without an early return

const name = callIf(session?.user, () => session.user.profile.displayName)

Chain of optional values

const label = callIf(row, () =>
  callIf(row.cell, () =>
    row.cell.text
  )
)

(The nesting is ugly here, but the point is each level only evaluates if the previous one passed.)

Gotchas

  • fn is not async-aware. If fn returns a Promise, you get Promise<T> | undefined, which is awkward to await. Wrap it: await callIf(cond, async () => ...) gives you T | undefined but the top-level await on a possibly-undefined value still needs a guard. There's no callIfAsync here by design — compose it yourself.
  • Truthiness is JS truthiness. callIf([], fn) runs fn, because [] is truthy. callIf("0", fn) runs fn. If you want a strict boolean, pass one: callIf(Boolean(cond), fn).
  • condition: any will let you write things TypeScript wouldn't normally allow. That's the tradeoff. It's on you to make sure the condition is actually meaningful.
  • Zero is falsy. callIf(0, () => "zero") returns undefined. If 0 is a valid trigger value, this is the wrong tool.

What this is not

  • Not lodash.get. It doesn't walk paths; it just gates a thunk.
  • Not optional-chaining. user?.name is a language feature and handles a narrow case. callIf handles arbitrary conditions and lazy computation.
  • Not a control-flow tool. If you have side effects you care about, use if. callIf is for producing a value, not for orchestrating behavior.

Philosophy

cond ? fn() : undefined is a perfectly good expression. callIf just gives it a name, so the intent is visible at the call site and the condition is evaluated exactly once. Use it wherever you'd otherwise reach for && and then have to explain why the falsy branch isn't what you expected.

clamp

Constrain a number to a range. One line. Returns value if it's already inside [min, max], otherwise returns the nearest bound.

clamp(5, 0, 10)     // 5
clamp(-3, 0, 10)    // 0
clamp(42, 0, 10)    // 10

That's the entire thing. Nothing else to know.

Usage

🟢 First-time users — start here

import { clamp } from "clamp"

clamp(5, 0, 10)      // 5
clamp(-100, 0, 10)   // 0
clamp(100, 0, 10)    // 10

That's it. You're done. You now know how to use clamp.

Real use:

const volume = clamp(userInput, 0, 1)          // normalize to 0–1
const age = clamp(parseInt(input), 18, 120)    // enforce bounds
const opacity = clamp(alpha, 0, 255)           // byte range

🔵 Everyone else

Signature

const clamp = (value: number, min: number, max: number): number
  • value — the number to constrain.
  • min — lower bound (inclusive).
  • max — upper bound (inclusive).
  • Returns value if min <= value <= max, otherwise min or max, whichever is nearer.

How it works

Math.min(max, Math.max(min, value))

Math.max(min, value) floors the value at min. Math.min(max, …) caps it at max. Composed, they produce the constrained result in a single expression with no branches.

Behavior notes

  • Bounds are inclusive. clamp(0, 0, 10) is 0. clamp(10, 0, 10) is 10. Nothing is off-by-one.
  • min > max is not guarded. If you pass clamp(5, 10, 0), you get 0 — Math.max(10, 5) is 10, then Math.min(0, 10) is 0. The function assumes min <= max. It doesn't validate, doesn't throw, doesn't swap. Garbage in, garbage out, fast.
  • NaN propagates. clamp(NaN, 0, 10) is NaN. Math.max and Math.min both return NaN if any argument is NaN.
  • Infinity works as a bound. clamp(x, -Infinity, Infinity) returns x. Useful for optional bounds.
  • Integers aren't enforced. clamp(3.7, 0, 10) is 3.7. This clamps, it doesn't round.

Common patterns

Normalizing user input

const level = clamp(parseInt(raw), 1, 100)

Clamping RGB / alpha channels

const r = clamp(channel, 0, 255)

Animation progress

const t = clamp((now - start) / duration, 0, 1)

Camera / scroll limits

scrollY = clamp(scrollY, 0, maxScroll)

Enforcing a range after arithmetic

Gotchas

  • No argument validation. min > max gives a surprising result rather than an error.
  • Does not coerce. Pass numbers. clamp("5", 0, 10) will produce "5" via Math.max's implicit coercion — don't rely on it.
  • Not variadic. Exactly three arguments.

deferred

A promise you settle from the outside. Create one, hand the promise to whoever is waiting, and call resolve or reject whenever you're ready.

const d = deferred<string>()

d.promise.then(v => console.log(v))   // not yet

d.resolve("hello")                     // logs "hello"

The point: separate creation of the promise from completion of it. The code that resolves and the code that awaits don't have to know about each other.

Usage

🟢 First-time users — start here

import { deferred } from "platform"

const d = deferred<User>()

// somewhere else — different function, different tick, different module
d.resolve(user)
// or
d.reject(new Error("failed"))

// wherever you need to wait
const user = await d.promise

That's it. You're done. You now know how to use deferred.

The promise is a normal promise. The resolve and reject are the normal settle functions. The only thing deferred does is let you keep them in separate scopes.

🔵 Everyone else

Signature

function deferred<T>(): {
  promise: Promise<T>
  resolve: (value: T) => void
  reject: (reason?: any) => void
}
  • promise — the pending promise. Hand it to anyone who needs to wait.
  • resolve(value) — settle the promise successfully with value.
  • reject(reason) — settle the promise with a rejection. reason can be anything; convention is an Error.

Both resolve and reject are the raw Promise executor callbacks. Only the first call to either has any effect; subsequent calls are no-ops. That's standard promise semantics, not a special guard in deferred.

How it works

let resolve!: (value: T) => void
let reject!: (reason?: any) => void
const promise = new Promise<T>((res, rej) => { resolve = res; reject = rej })
return { promise, resolve, reject }

Three lines of logic:

  1. Declare resolve and reject with definite-assignment assertions (!) — they'll be set synchronously inside the executor.
  2. Create the promise. The executor runs synchronously, so res and rej are captured into the outer variables before the constructor returns.
  3. Return the promise and the two callbacks as a single object.

There's no other state. No settled flag, no value cache, no guard. The promise machinery is the state.

Why you'd want this

The normal way to create a promise is to write the executor at the same place the promise is used:

const p = new Promise<Value>((resolve, reject) => {
  // resolve/reject are only reachable inside this callback
})

The executor is a "resolver scope." Any code that needs to call resolve has to live inside it, or be wired up through a callback that is. That's fine when the resolution happens in the same logical place — a fetch callback, a setTimeout, an event handler.

It's awkward when the code that will resolve the promise lives elsewhere — a different module, a different function, a registry of pending operations. deferred extracts resolve and reject into a return value so you can hand them around.

Common situations where this matters:

  • A queue of pending requests that resolves each one when a response arrives.
  • A registry of waiters keyed by id — someone calls register(id), the deferred goes into a map, a response comes in, the deferred for that id is resolved.
  • Bridging callback APIs to promise APIs — pass resolve and reject where the callback API expects them.
  • Manually controlled test promises — resolve at a specific moment.
  • Promise-based handoffs where the resolver is determined after the promise is created.

Common patterns

Bridging a callback API

function readAsync(path: string) {
  const d = deferred<Buffer>()
  fs.readFile(path, (err, data) => {
    if (err) d.reject(err)
    else d.resolve(data)
  })
  return d.promise
}

This is what new Promise does internally. deferred just makes the intermediate explicit.

Waiter registry

const waiters = new Map<string, ReturnType<typeof deferred<Response>>>()

function expect(id: string) {
  const d = deferred<Response>()
  waiters.set(id, d)
  return d.promise
}

function deliver(id: string, res: Response) {
  const d = waiters.get(id)
  waiters.delete(id)
  d?.resolve(res)
}

expect(id) returns a promise. deliver(id, res) resolves it. Neither one has to know about the other's call site.

Manually controlled promise in tests

const gate = deferred<void>()
fetchMock.mockImplementationOnce(() => gate.promise)

const call = fetchUser(id)
// ... assert on intermediate state ...
gate.resolve()

await call

Coordinating between async branches

const connected = deferred<void>()

client.on("connect", () => connected.resolve())
client.on("error", e => connected.reject(e))

await connected.promise

Behavior

  • resolve(value) settles the promise with value. If value is a promise or thenable, the outer promise adopts it — same as Promise.resolve.
  • reject(reason) settles the promise with a rejection. reason can be anything; it's not coerced.
  • First call wins. Calling resolve twice is a no-op the second time. Calling resolve after reject is a no-op. Standard promise semantics.
  • No settled flag. The type doesn't expose whether the deferred has been settled. If you need that, track it separately or check await Promise.race([d.promise.then(() => "resolved", () => "rejected"), Promise.resolve("pending")]).
  • The promise starts pending. If you never call resolve or reject, it stays pending forever. No timeout, no auto-settle.
  • resolve and reject are the raw executor callbacks. They don't return anything, don't throw if called late, and don't validate their argument.

deferred vs gate

Sibling primitives with different failure models:

  • deferred<T> — both resolve and reject. The failure case exists.
  • gate<T> — only open. No rejection. Readiness has no failure mode.

Pick by the domain. "Did the request succeed?" → deferred. "Is the subsystem ready?" → gate.

The other difference: gate names its resolve open, which reads as a signal rather than a completion. deferred uses the standard resolve / reject names, matching the promise executor.

deferred vs Promise.withResolvers

Promise.withResolvers<T>() is the native version of the same thing. Same shape, same semantics:

const { promise, resolve, reject } = Promise.withResolvers<T>()

deferred predates it or backfills it for environments where Promise.withResolvers isn't available. If your runtime has Promise.withResolvers, either one works — deferred has the advantage of being a single import that works everywhere.

Gotchas

  • Handing out resolve / reject is handing out control. Anyone with a reference can settle the promise. If that's not what you want, keep the deferred in the enclosing scope and expose only .promise.
  • No protection against double-settle. First call wins silently. If two producers race to resolve, whichever runs first is what the waiter sees; the second's value is dropped without a warning.
  • No protection against late settle. Calling resolve after the promise was already rejected is a no-op. There's no way to detect that from inside deferred.
  • Rejection with a non-Error is allowed. d.reject("oops") is valid; the promise rejects with the string. Consumers expecting Error will need to handle it. Convention is to always reject with Error instances.
  • Memory: the promise holds a reference. A deferred that is never settled and never awaited still holds the promise object, and if consumers added .then callbacks, those callbacks are never invoked and their closures stay alive. Watch for leaked deferreds in registries.
  • No cancellation. Once created, the deferred exists until settled or garbage collected. There's no cancel() method. If you need cancellation, wrap the promise with AbortSignal on the consumer side, or design your registry to remove entries.
  • The ! on resolve and reject is a TypeScript definite-assignment assertion. It tells the compiler "these will be set before use." The promise executor runs synchronously, so they are. Don't move the promise construction after the return and expect this to still hold.

What this is not

  • Not a Deferred with a .resolve() method. It's a plain object with three fields. Call d.resolve(x), not d.resolve()(x).
  • Not cancellable, resettable, or observable. It's a one-shot.
  • Not a queue. It resolves one thing.
  • Not a thenable itself. The deferred object isn't a promise; its .promise field is. Don't await d, await d.promise.

Philosophy

new Promise ties the resolver to the executor scope. That's usually fine and occasionally awkward. deferred pulls the resolver out into a value so it can be handed to whoever needs it — a registry, a callback adapter, another module. Three lines, no state beyond what the promise machinery provides, the same failure model as the promise executor itself.

evaluator

Classify any JavaScript value by shape. Returns a short string tag — "thenable", "async-iterable", "map", "plainObject", "number", etc. — describing what the value is, not what it contains.

evaluator(async function* () {}) // "async-iterable"
evaluator(new Map())             // "map"
evaluator({ a: 1 })              // "plainObject"
evaluator(42)                    // "number"

The point: one function that answers "what kind of thing is this?" without a chain of typeof checks at every call site. Useful for dispatch, logging, serialization, and validation.

🔵 Everyone else

Signature

The full tag list

In the order the checks run:

Order Tag Matches
1 "thenable" anything with a .then function (Promise, thenable, some libraries' lazy values)
2 "async-iterable" has [Symbol.asyncIterator]
3 "null" null (typeof is "object", so it's separate)
4 "string" / "number" / "boolean" / "bigint" / "symbol" / "undefined" primitives (from typeof v)
5 "function" functions
6 "array" TypedArrays and DataViews (ArrayBuffer.isView)
7 "map" instanceof Map
8 "set" instanceof Set
9 "date" instanceof Date
10 "regexp" instanceof RegExp
11 "error" instanceof Error
12 "iterable" has [Symbol.iterator]
13 "object" anything else with typeof === "object" (plain record, or fallback)

That's the set. Some lines in the source run after a return that already fired for any reachable input — see the analysis below.

Why the order is what it is

Two axes matter: async-ness and shape.

  1. Async first. thenable and async-iterable are checked before anything else. If a value is a promise or an async iterable, that's the most important thing about it — more than whether it's also an object. So those win.
  2. Null before object. typeof null === "object" is a famous JS wart. Null is checked explicitly so it doesn't fall into the "object" bucket.
  3. Primitives before objects. typeof returns a definitive string for primitives; no further checks needed.
  4. Specific classes before generic ones. Map, Set, Date, RegExp, Error are checked before the generic "object" fallback, so a Map doesn't get classified as a plain object.
  5. Iterables last before "object". Arrays, Strings, Maps, Sets all have Symbol.iterator. But Map, Set, String, Array are all caught earlier — so "iterable" only fires for custom iterables that aren't one of the known types.

Common patterns

Dispatch by kind

  case "thenable": return await v
  case "iterable": return [...v]
  case "map": return [...v.entries()]
  case "set": return [...v.values()]
  case "object": return Object.entries(v)

Logging

Serialization decisions

if (kind === "date") return v.toISOString()

Behavior

  • First match wins. Once a check hits, the function returns immediately. Later checks never run.
  • typeof null === "object" is handled explicitly — null gets its own tag, not "object".
  • instanceof checks are realm-sensitive. In a multi-realm environment (iframes, workers, vm contexts), Map, Set, Date, etc. from a different realm will fail their instanceof check. Array.isArray is cross-realm-safe; the instanceof checks are not.
  • No valueOf / toString calls. The classifier doesn't coerce, doesn't serialize. It only inspects shape.
  • Thenables win over everything. A Map with a .then method would be "thenable", not "map". This is by design — async-ness takes precedence.

Finally

Run a function for its side effect, return the value unchanged. Same shape as tap, but named for the intent: "do this cleanup / teardown / bookkeeping in passing, and hand the value back."

return Finally(computeResult(), () => cleanup())
// → cleanup runs, computeResult()'s value is returned

The point: inject a "finally" into an expression. Where a try / finally block would run fn before returning, Finally(value, fn) runs fn before returning the value — inside a single expression, no statement, no variable.

Usage

// logs "done", x is whatever doWork() returned

That's it. You're done. You now know how to use Finally.

It's fn() then return value. The value goes through; the function runs on the way.

🔵 Everyone else

Signature

function Finally<T>(value: T, fn: () => any): T
  • value — anything. Object, primitive, promise, whatever.
  • fn — a function called with no arguments. Its return is discarded.
  • Returns value. The same reference for objects, the same value for primitives.

How it works

fn()
return value

Two lines. fn runs for its side effect; its return value is ignored. value is returned as-is.

Relationship to tap

Finally is tap with the arguments flipped into a different shape and the name changed. Both do the same thing mechanically:

tap(value, fn)         // run fn(value), return value
Finally(value, fn)     // run fn(),      return value

The differences:

tap Finally
Passes value to fn yes no
fn signature (value: T) => any () => any
Name connotes observing a value running cleanup

If fn needs the value (logging it, asserting on it, emitting it as a payload), use tap. If fn just needs to run — cleanup, bookkeeping, closing a handle — use Finally.

Neither function is more correct. They're the same trick with different ergonomics. Pick by what reads better at the call site.

Why the name

"Finally" is borrowed from try / finally. In a try block:

try {
  return compute()
} finally {
  cleanup()
}

The finally runs after the try body, on the way out. Finally(value, fn) is the expression form of the same idea: fn runs after value is produced, on the way to being returned.

The capital F distinguishes it from the keyword and from Promise.prototype.finally. It's a function, not a control structure — but the name signals the same intent.

Common patterns

Cleanup on the way out

Bookkeeping after a computation

return Finally(compute(), () => metrics.increment("compute.done"))

Closing a handle

return Finally(readFile(path), () => handle.close())

Committing a transaction

return Finally(applyChanges(tx), () => tx.commit())

Logging a boundary

return Finally(result, () => log.info("operation complete"))

Composing with other helpers

  orDefault(response.data, {}),
  () => cache.set(key, response.data),
)

Behavior

  • Same reference for objects. Finally(obj, fn) === obj. Not a copy, not a clone.
  • Same value for primitives. Finally(42, fn) === 42.
  • fn runs before the return. If fn throws, Finally throws and the value is not returned.
  • fn is synchronous. No awaiting, no deferral. If fn returns a promise, the promise floats — potentially unhandled.
  • fn takes no arguments. Unlike tap, it doesn't receive the value. If you need it, use tap.
  • fn's return is discarded. Whatever fn returns has no effect on the result.
  • fn is called exactly once. No retry, no reentrancy protection. Called once, per call to Finally.

gate / reGate

A promise you open manually. gate is one-shot — you hold the promise, you call open(value) when the thing is ready. reGate is the resettable version — you can close it back up and reuse it for the next round.

There is no rejection. There is no failure. A gate opens or it doesn't, and the waiter decides how long they're willing to wait.

const g = gate()
ready.once("load", () => g.open())
await g.promise   // resolves when ready fires "load"

The point: separate when the thing is ready from how long the waiter is willing to wait. The gate has no opinion about time. wait(ms) on the caller's side does. gate is timeless; the wait has a time.

Usage

🟢 First-time users — start here

import { gate, reGate } from "platform"

const g = gate()

// somewhere else — maybe another file, another tick, another module
g.open()

// wherever you need to wait
await g.promise

That's it. You're done. You now know how to use gate.

The promise resolves when someone calls open(). If nobody ever does, it never resolves — no rejection, no error, just a pending promise. If you want a timeout, race it with your own:

await Promise.race([g.promise, timedPromise(new Promise(() => {}), 5000)])

Or use the platform's wait(ms) if it ships one. The gate doesn't know about the timeout. The waiter does. That asymmetry is the design.

For the reusable version:

g.open(1)
console.log(await first)   // 1

g.reset()                  // ready for the next round

g.open(2)
console.log(await second)  // 2

Signatures

function gate<T = void>(): {
  promise: Promise<T>
  open: (v: T) => void
}

function reGate<T = void>(): {
  readonly promise: Promise<T>
  readonly opened: boolean
  open: (v: T | PromiseLike<T>) => void
  reset: () => void
}

gate — the one-shot

function gate<T = void>() {
  let resolve!: (v: T) => void
  const promise = new Promise<T>(r => { resolve = r })
  return { promise, open: resolve }
}

Three lines of logic:

  1. Create a promise whose resolve function is captured in a local.
  2. Return { promise, open } where open is the captured resolve.
  3. Call open(value) to resolve promise with value.

gate is Promise.withResolvers with a smaller name and a default of void. That's the entire implementation.

Why no reject

The doc comment says it: "It's deferred minus the failure case." A Deferred has both resolve and reject. gate deliberately drops reject. The justification:

"Wait for this thing to be ready" is not a thing that fails. It just takes longer than you're willing to wait.

Readiness is not a failure mode. There's no "the thing became un-ready." There's no "the ready event threw." The gate opens, or it stays closed. If a caller decides they've waited too long, that's the caller's decision, and it's a decision about the wait, not about the gate.

Why the timeout is the caller's job

gate has no wait(ms) method. No timeout, no cancellation, no abort. The gate is timeless. The caller brings the bound:

const g = gate()
// ... later ...
await Promise.race([g.promise, sleep(5000).then(() => { throw new Error("timeout") })])

Or, if the platform ships a wait(ms) that wraps a gate with a timeout, use that. wait(0) means "wait forever" (no timeout); wait(5000) means "give up at 5s." Both are correct because the wait has a time, and the gate doesn't.

This is the asymmetry the design is built on. A gate that had a built-in timeout would be making a policy decision on behalf of every waiter. Two waiters with different tolerances would fight over the same timeout. By pushing the timeout to the caller, each waiter chooses their own.

reGate — the resettable version

function reGate<T = void>() {
  let open!: (v: T | PromiseLike<T>) => void
  let promise: Promise<T>
  let opened = false

  const reset = () => {
    opened = false
    promise = new Promise<T>(resolve => open = resolve)
  }

  const release = (v: T | PromiseLike<T>) => {
    if (opened) return
    opened = true
    open(v)
  }

  reset()

  return {
    get promise() { return promise },
    get opened() { return opened },
    open: release,
    reset,
  }
}

Same shape as gate, plus two things:

  • reset() — closes the gate and creates a fresh promise. The old promise is abandoned (it will never resolve if it hadn't already). Callers who captured the old .promise are stuck with it; callers who re-read .promise get the new one.
  • opened — a getter that reports whether the gate has been opened since the last reset. Useful for "did anything already happen while I was setting up?"

ignoreArg

Adapt a zero-argument callback to an API that passes an argument. Wraps your function, discards whatever the caller sends, and invokes your function with no arguments.

The point: React, the DOM, and most event systems hand every handler an event object. When your callback doesn't take arguments — which is most of the time — ignoreArg bridges the two shapes so the handler slot accepts a function the API would otherwise reject or that would force you to write () => inline.

🔵 Everyone else

Signature

const ignoreArg = <T>(fn: () => T) => (_arg?: unknown) => fn()

Two functions. Outer takes your callback; the returned function is the adapter that accepts any argument and ignores it.

  • ignoreArg(fn) returns (_arg?) => fn().
  • The adapter accepts an optional argument of any shape and discards it.
  • Calling the adapter calls fn() with no arguments and returns whatever fn returns.

When to use it

The use case is narrow and specific: the caller passes an argument, the callee doesn't accept one, and the type signatures are incompatible without a wrapper.

Common situations:

  • React event handlers typed as (e: Event) => void. Passing a () => void function directly is a type error in strict configs. ignoreArg bridges it.
  • addEventListener callbacks. The DOM passes an event; your callback doesn't take one.
  • Pub/sub bus handlers. The bus invokes with a payload; your handler ignores it.
  • Third-party UI libraries whose prop types require an argument where you don't need one.
element.addEventListener("click", ignoreArg(handleClick))

ignoreArg vs an inline arrow

Both do the same thing:

onClick={() => toggle()}          // inline arrow ignores the event
onClick={ignoreArg(toggle)}       // adapter ignores the event

Pick ignoreArg when:

  • You want the call site to read as "the argument is intentionally dropped."
  • You're passing a named function you'd rather not wrap inline.
  • You're producing handlers that will be stored, passed, or reused (bus handlers, config objects).

Pick the inline arrow when:

  • It's obvious from context that the argument doesn't matter.
  • You're already in an expression and another function call adds noise.

Neither is more correct. ignoreArg names the intent; the arrow just performs it.

Behavior

  • The argument is discarded. Not logged, not forwarded, not inspected. Whatever the caller sends is dropped on the floor.
  • fn is called with no arguments. Even if fn is defined to accept parameters, they arrive as undefined. TypeScript accepts this because fn is typed () => T.
  • Return value passes through. If fn returns a value, the adapter does too.
  • New adapter per call. ignoreArg(fn) !== ignoreArg(fn). See gotchas for the React identity implications.
  • Synchronous. The adapter is not async; it doesn't await, wrap, or defer. Whatever fn returns is whatever the adapter returns.

The point: React (and DOM, and most event systems) pass an event object to every handler. When you don't care about the event — which is most of the time — invoke gives you a wrapper that swallows the argument and calls your function with no arguments.

Signature

Two functions. The outer takes your function, the inner is the event handler.

  • invoke(fn) returns (_event?) => fn().
  • The returned handler accepts an optional event and ignores it.
  • Calling the handler calls fn() with no arguments and returns whatever fn returns.

Why you'd want this

In React (and most event-driven APIs), handlers receive an event as their first argument:

<button onClick={(e) => ...}>

If you don't need the event, you have two options:

// inline thunk — the event is right there, ignored
<button onClick={() => setOpen(true)}>

  • The event is discarded. Not logged, not forwarded, not inspected. Whatever the caller passes is ignored.
  • The inner function takes an optional parameter. Typed _event?: unknown, so it works with handlers that pass an event, handlers that pass nothing, and handlers that pass something else.
  • Returns whatever fn() returns. If fn returns a value, the handler does too. If fn returns void, the handler returns void.
  • Creates a new handler on each call to invoke. invoke(fn) !== invoke(fn). This is the usual gotcha for React reconciliation — see below.

isDefined

A type guard that answers one question: is this thing neither null nor undefined? If yes, TypeScript narrows the type to remove both.

const xs: (number | null | undefined)[] = [1, null, 2, undefined, 3]
const defined = xs.filter(isDefined)   // number[]

Usage

🟢 First-time users — start here

import { isDefined } from "is-defined"

isDefined(0)          // true
isDefined("")         // true
isDefined(false)      // true
isDefined(null)       // false
isDefined(undefined)  // false

That's it. You're done. You now know how to use isDefined.

The reason you'd use it instead of writing x != null inline is the filter case:

const values = [1, null, 2, undefined, 3].filter(isDefined)
// values: number[]

Without the type guard, TypeScript would keep null | undefined in the element type and you'd be stuck asserting.

🔵 Everyone else

Signature

const isDefined = <T>(x: T | null | undefined): x is T

It's a type predicate — x is T — which tells the compiler that a truthy return narrows x from T | null | undefined to just T. That narrowing is what makes .filter(isDefined) produce T[] instead of (T | null | undefined)[].

Why x != null and not x !== null && x !== undefined

!= with null matches both null and undefined in one comparison. It's the only place in JS where loose equality is the correct, idiomatic choice — and linters that flag it universally are wrong about this specific case.

null      != null   // false
undefined != null   // false
0         != null   // true
""        != null   // true
false     != null   // true
NaN       != null   // true

So the predicate is true for every value that isn't null or undefined, including all the falsy-but-real values.

Why not .filter(Boolean)

Boolean is a valid filter predicate at runtime but it has no narrowing type signature. TypeScript sees .filter(Boolean) and keeps the original element type — you still have null | undefined in the array as far as the compiler is concerned. isDefined exists precisely to fix that.

const xs = [1, null, 2, undefined, 3]

xs.filter(Boolean)     // (number | null | undefined)[]  ← compiler disagrees with reality
xs.filter(isDefined)   // number[]                        ← correct

Common patterns

Cleaning up arrays

const users = raw.map(parseUser).filter(isDefined)

Guard before a deref

if (isDefined(maybeConfig)) {
  return maybeConfig.timeout   // narrowed — no `?.`, no `!`
}

Object entries where values may be missing

const entries = Object.entries(map).filter(([, v]) => isDefined(v))

Type guard in a union check

function process(x: string | null | undefined) {
  if (!isDefined(x)) return
  // x: string
}

What it accepts

  • null → false
  • undefined → false
  • 0, "", false, NaN → true (these are values, not absences)
  • anything else → true

The distinction that matters: isDefined is about presence, not truthiness. 0 is defined. "" is defined. Empty arrays are defined. Only the two nullish sentinels are "not defined."

Type guard for the nullish check. false when the value is neither null nor undefined; true when it's one of them. Pairs with isDefined as the inverted predicate.

Signature

A type predicate. Truthy return narrows the positive branch — but note the semantics are inverted from isDefined: this returns true when the value is nullish. The v is T predicate is what TypeScript attaches to the truthy case, which for this function is the "value is nullish" case. In practice you use it in .filter and in if (!isNotDefined(x)) guards, where the narrowing lands where you want it.

Same reason as isDefined: loose != against either nullish sentinel matches both. v != undefined is false for every non-nullish value and true for null and undefined. One comparison, both cases.

null      != undefined   // false  → isNotDefined(null) === true
undefined != undefined   // false  → isNotDefined(undefined) === true
0         != undefined   // true   → isNotDefined(0) === false
""        != undefined   // true   → isNotDefined("") === false
false     != undefined   // true   → isNotDefined(false) === false
NaN       != undefined   // true   → isNotDefined(NaN) === false

Falsy-but-real values (0, "", false, NaN) are defined. Only the two sentinels are "not defined."

They're exact inverses. Both do the same nullish check; they differ only in which side of the branch they return true on.

Value isDefined isNotDefined
null false true
undefined false true
0 true false
"" true false
false true false
NaN true false
{} true false

Pick by what you're collecting or guarding against. filter(isDefined) keeps the real values. filter(isNotDefined) keeps the holes.

  get value(): T
}

The constructor takes a factory — a zero-argument function. Not a value. That's the whole contract: Lazy never runs the factory until .value is read, and never runs it more than once.

How it works

get value(): T {
  if (!this._isValueCreated) {
    this._value = this._factory()
    this._isValueCreated = true
  }
  return this._value!
}
  • First .value read: flag is false, factory runs, result is cached, flag is set, result returned.
  • Every subsequent read: flag is true, branch is skipped, cached value returned.
  • _isValueCreated is set after the factory returns, so a factory that throws leaves the lazy uninitialized and the next read will try again. This is a design choice — see gotchas.
  • _value is typed T | null internally and asserted ! on the return path. The ! is safe because the branch guarantees it was just set.

isValueCreated — the point of the interface

Reading .value always runs the factory if it hasn't run yet. Sometimes you want to ask whether the work has been done without doing it. That's what .isValueCreated is for:

if (lazy.isValueCreated) {
  // safe to read .value without triggering the factory
  const v = lazy.value
}

This is why Lazy exposes an interface at all — you can hand a consumer an ILazy<T> and let them decide whether to pay the cost. Same value either way, but the consumer can make the call.

Common patterns

Dependency slots

class Service {
  private _db = new Lazy(() => openDb(config.connectionString))
  get db() { return this._db.value }
}

The service can be constructed without a database. The first thing that touches .db pays the connection cost. Nothing else does.

Module-level singletons

const registry = new Lazy(() => buildRegistry())
export const getRegistry = () => registry.value

Circular dependency breaks

const a = new Lazy(() => new A(b.value))
const b = new Lazy(() => new B(a.value))

Neither constructor runs until .value is read, at which point both resolve.

Conditional expensive work

const preview = new Lazy(() => renderFullPreview(doc))

if (userWantsPreview) {
  return preview.value   // pays the cost
}
return null              // never pays

Behavioral guarantees

  • At most once. The factory runs on the first .value read and never again, even across many readers.
  • Synchronous. The factory is called synchronously on the read. If the factory does async work, .value will be a Promise<T>, not T — Lazy does not unwrap promises.
  • Not thread-safe in the traditional sense — but JS is single-threaded, so concurrent readers can't race. Two readers in the same tick will both see the same result; whichever reads first pays the cost.
  • No reset. Once initialized, there's no way to clear the cache. Create a new Lazy if you need a new value.

once

Wrap a function so it only ever runs the first time it's called. Every call after returns the first call's result. Same function, same arguments — but the body executes exactly once, ever.

const init = once(() => connectToDatabase())

init()   // runs connectToDatabase()
init()   // returns the same connection
init()   // returns the same connection

Two variants ship together: once for zero-argument factories, onceB for functions with arguments that need to preserve their signature. Both are cached-forever wrappers.

Usage

🟢 First-time users — start here

import { once } from "platform"

const getConfig = once(() => ({
  env: process.env.NODE_ENV,
  started: Date.now(),
}))

getConfig()   // builds the object
getConfig()   // same object, same timestamp

That's it. You're done. You now know how to use once.

The short version: wrap a function, call it as many times as you want, the body only runs on the first call. Every call returns the same result.

With arguments, use onceB:

const parse = onceB((json: string) => JSON.parse(json))

parse('{"a":1}')   // parses, returns { a: 1 }
parse('{"b":2}')   // returns { a: 1 } — arguments ignored after the first call

🔵 Everyone else

The two variants

function once<T>(fn: () => T): () => T
function onceB<F extends (...args: any[]) => any>(fn: F): F
  • once(fn) — takes a zero-argument factory, returns a zero-argument function. Cleanest signature, no args machinery.
  • onceB(fn) — takes any function, returns the same signature. Arguments are accepted on every call but only used on the first one. After that, the arguments are discarded and the cached result is returned.

The B suffix is for "bound" or "blind" — it preserves the type signature of the wrapped function. Pick once when you have a factory with no parameters. Pick onceB when you want to wrap an existing function and keep its type.

How they work

Both use the same pattern: a done/called boolean and a cached value.

let cached: T
let done = false
return () => {
  if (!done) {
    cached = fn()
    done = true
  }
  return cached
}
  • First call: flag is false, fn runs, result cached, flag set, result returned.
  • Every subsequent call: flag is true, fn is skipped, cached result returned.
  • The flag is set after fn returns. If fn throws, the flag stays false and the next call retries. Same semantics as Lazy.

onceB is identical except it spreads ...args into the first fn call and ignores them after.

Why two functions instead of one

once has a tight, precise signature: () => T. No any, no generic function type, no as F cast.

onceB needs F extends (...args: any[]) => any to accept any function shape and as F on the return to hand the signature back. That's the cost of generality. If you have a zero-arg factory, once is strictly better — no casts, no spread, no any.

Common patterns

Idempotent initialization

const ensureInit = once(() => {
  registerHandlers()
  startTelemetry()
  return true
})

ensureInit()   // runs the setup
ensureInit()   // no-op

Module-level singleton

const getPool = once(() => new ConnectionPool(config))

Expensive parse, called from many places

const schema = onceB((raw: string) => compileSchema(raw))

// first caller's input wins — subsequent callers get the first schema
const s1 = schema(inputA)
const s2 = schema(inputB)   // returns s1

Guarding against double-registration

const register = onceB((name: string) => registry.add(name))
register("a")   // adds "a"
register("b")   // no-op, returns the result of the first call

Deferred work that may never fire

const flush = once(() => queue.drain())
// call flush() from every exit path; only the first one actually flushes

Behavioral guarantees

  • At most once. The wrapped function runs on the first call and never again.
  • Same return value, always. Every call returns the identical reference (or primitive) from the first call.
  • Arguments ignored after the first call in onceB. No memoization per argument set — it's a single-shot cache, not a keyed cache.
  • Synchronous. once doesn't await, doesn't unwrap promises. If fn returns a Promise<T>, the wrapper returns that same promise on every call — which is usually the right behavior for async singletons.
  • Throws propagate. If fn throws on the first call, the error propagates and the wrapper is not marked done. The next call retries.

once vs Lazy

Both cache a single value forever. The difference is shape:

  • Lazy<T> wraps a factory and exposes .value (a property) plus .isValueCreated (inspect without triggering).
  • once(fn) wraps a function and returns a function. No .isValueCreated, no property access — you call it.

Use Lazy when you want to pass the value slot around. Use once when you want to pass a callable around.

orDefault

Return the value if it's neither null nor undefined. Otherwise return the fallback. One line, one operator, no ceremony.

orDefault(user?.name, "Anonymous")    // "Anonymous" if name is nullish
orDefault(count, 0)                    // 0 if count is nullish
orDefault(config, defaults)            // defaults if config is nullish

The point: collapse the nullish check and the fallback into a single expression that names itself at the call site.

Usage

🟢 First-time users — start here

import { orDefault } from "platform"

const name = orDefault(input.name, "Anonymous")
const count = orDefault(input.count, 0)

That's it. You're done. You now know how to use orDefault.

It's ?? with a name. Pass a value and a fallback; you get the value if it exists, the fallback if it doesn't. null and undefined are the only triggers.

🔵 Everyone else

Signature

const orDefault = <T>(value: T | null | undefined, fallback: T): T
  • value — the value to check. May be T, null, or undefined.
  • fallback — what to return if value is nullish. Must be a T.
  • Returns T. Never null, never undefined.

The two Ts are the same type. The fallback is not a different shape — it's the same shape, chosen to stand in when the value is missing.

How it works

value ?? fallback

?? (nullish coalescing) returns the left side unless it's null or undefined, in which case it returns the right side. It's exactly the semantics of the function. The function exists to give the operator a name and a place in the codebase.

Why a name at all

?? is a fine operator. The reasons to wrap it:

  • Readability at the call site. orDefault(x, fallback) reads like what it does. x ?? fallback is fine, but the named version composes better with other helpers and reads as intent, not syntax.
  • One spelling. If you want to change the fallback policy across the codebase — say, to also treat empty strings as missing — you change one function.
  • Composition. orDefault slots into pipelines and higher-order utilities where ?? can't (it's an operator, not a value).
  • Type narrowing in complex cases. Occasionally the compiler needs the explicit signature to infer T correctly, especially with union types.

None of these is a huge win. The function is convenience, not necessity. That's fine — the same is true of isDefined over x != null, and we ship that too.

Behavior

  • null → fallback.
  • undefined → fallback.
  • Everything else → the value itself. Including 0, "", false, NaN, [], {}.
  • Fallback is returned by reference. If the fallback is an object, callers get the same object every time. No cloning.

The last point matters. Unlike ||, ?? (and therefore orDefault) does not treat falsy values as missing:

orDefault(0, 10)         // 0
orDefault("", "default") // ""
orDefault(false, true)   // false
orDefault(NaN, 42)       // NaN

If you wanted the || behavior — treat any falsy as missing — you want a different function. This one is nullish-only, on purpose.

Common patterns

Optional config with defaults

const timeout = orDefault(options.timeout, 5000)
const retries = orDefault(options.retries, 3)

Display fallbacks

const displayName = orDefault(user.nickname, user.email)

Filling in arrays or objects

const items = orDefault(response.items, [])
const meta = orDefault(response.meta, {})

Chained defaults

const port = orDefault(env.PORT, orDefault(config.port, 3000))

Inside a Chain or ReChain pipeline

new ReChain(input).set("name", orDefault(input.name, "Anonymous")).done()

Converting possibly-nullish to definite

function process(input: string | null | undefined) {
  const s = orDefault(input, "")
  return s.toUpperCase()   // s is string, no null check needed
}

patchState

Merge a partial object into React-style state via the functional updater. Never reads state from the render closure, so no stale-closure bugs. Just { ...prev, ...patch }, wrapped, named, and ready to call.

patchState(setUser, { name: "Alice", age: 30 })
// → setUser(prev => ({ ...prev, name: "Alice", age: 30 }))

The multi-field version of setKey. One call, one spread, one state update.

Usage

🟢 First-time users — start here

import { patchState } from "platform"

patchState(setForm, { name: "Alice", age: 30 })
patchState(setUser, { lastSeen: Date.now() })

That's it. You're done. You now know how to use patchState.

It's the same as writing setForm(prev => ({ ...prev, name: "Alice", age: 30 })) — but the correct pattern is baked in, so you can't accidentally reach for stale state.

🔵 Everyone else

Signature

function patchState<T = any>(setState: any, patch: Partial<T>): void
  • setState — a React-style setter. Typed any (see gotchas).
  • patch — a partial object whose keys are merged over the current state.
  • Returns void.

Partial<T> on the patch is the type-level contract: every field is optional, so you can update a subset. The T default is any, but inference from patch usually narrows it if the patch is typed.

How it works

setState((prev: any) => ({ ...prev, ...patch }))

One line. It builds the functional updater and hands it to the setter. prev is whatever the latest state is when React applies the update — never the state captured in the render closure that called patchState.

The result is a shallow clone of prev with the patch's keys replaced. Fields not mentioned in the patch are unchanged.

The point of the functional form

// ❌ reads stale state if called twice in the same tick, or after an await
setState({ ...state, name: "Alice" })

// ✅ always reads the latest state
setState(prev => ({ ...prev, name: "Alice" }))

The direct-object form works in tests and breaks in production. patchState makes the functional form the only form — you can't reach for stale state because the helper never gives you a way to.

This matters most when:

  • The same setter is called twice in one event handler.
  • The setter is called after an await.
  • A parent re-renders between the call and the state application.

In all three cases, the direct-object form silently loses the earlier update. patchState never does.

Common patterns

Multi-field form updates

<button onClick={() => patchState(setForm, { submitted: true, error: undefined })}>
  Submit
</button>

Merging a partial response

patchState(setUser, { lastSeen: Date.now(), online: true })

Resetting a subset of fields

patchState(setForm, { name: "", email: "", error: undefined })

Composing two patches

patchState(setState, { a: 1 })
patchState(setState, { b: 2 })
// both land — the second updater runs against the first's result

From inside an async handler

async function save() {
  const res = await api.put(data)
  patchState(setUser, { lastSaved: res.timestamp })
  // still correct even if other updates happened during the await
}

Behavior

  • Shallow clone. { ...prev, ...patch } creates a new object at the top level. Nested objects from prev are shared by reference unless the patch replaces them.
  • Functional updater. Always reads the latest prev.
  • Never mutates prev.
  • Fields not in the patch are untouched. patchState(setState, {}) produces { ...prev } — a shallow clone with no changes. Harmless but wasteful; avoid empty patches.
  • undefined values in the patch overwrite. patchState(setState, { error: undefined }) sets error to undefined. The key still exists on the object; JSON serialization drops it, but Object.keys and iteration still see it.
  • Last writer wins on shared keys. If two calls in the same tick both touch name, the second one's value is what ends up on the object.
  • Synchronous call to the setter. The updater is built and handed off; React schedules the actual render.

Differences from setKey

Both update state via the functional form. The differences:

setKey patchState
Fields one many
Types key: K, value: T[K] patch: Partial<T>
Argument shape two scalars one object
Type inference from key/value from patch
Use when one field several fields

Use setKey when you're setting exactly one field — you get per-key type checking on the value. Use patchState when you're updating a group of fields at once and the patch object is natural to write.

Differences from setPrev

setPrev has two modes: single-key when k is provided, merge when it's not. patchState is only the merge mode. If you're using setPrev without a k every time, patchState is the clearer name for the same behavior.

retryWithBackoff

Retry an async attempt up to N times with exponential backoff, a delay cap, and cooperative cancellation. Returns the first defined value the attempt produces, or undefined if every attempt fails, returns undefined, or the operation is cancelled.

const user = await retryWithBackoff({
  attempt: async (n) => fetchUser(id),
})
// → the user, or undefined if all 4 attempts failed

Built for the React/useEffect case: an isCancelled callback checked at every await boundary, so an unmounted component never resolves into stale state.

Usage

🟢 First-time users — start here

import { retryWithBackoff } from "platform"
import { useEffect, useState } from "react"

useEffect(() => {
  let cancelled = false
  retryWithBackoff({
    isCancelled: () => cancelled,
    attempt: async (n) => {
      return fetchData()   // whatever you're trying to get
    },
  }).then(setData)
  return () => { cancelled = true }
}, [])

That's it. You're done. You now know how to use retryWithBackoff.

The pattern is always the same:

  1. Set a cancelled flag in the effect body.
  2. Pass isCancelled: () => cancelled to the retry call.
  3. Flip cancelled in the cleanup function.

The retry loop checks the flag before each attempt, between attempts, and after the sleep — so once the component unmounts, no further work happens and no stale value is resolved into state.

🔵 Everyone else

Signature

function retryWithBackoff<T>({
  attempts?: number,           // default 4
  baseDelayMs?: number,        // default 1000
  maxDelayMs?: number,         // default 12000
  isCancelled?: () => boolean, // default () => false
  attempt?: (n: number) => Promise<T | undefined>,
  onAttemptFailed?: (n: number, e: unknown) => void,
  onGiveUp?: () => void,
}): Promise<T | undefined>

Every option has a default, and the two callbacks have default console.log implementations. You can call it with just { attempt } and it will retry up to 4 times with 1s / 2s / 4s / 8s delays, capping at 12s.

What attempt must return

attempt(n) receives the attempt number starting at 1 and must return the value you want, or undefined to signal "try again." This is different from "throw on failure." Both are supported:

  • Return undefined → treated as "not ready, retry."
  • Throw or reject → onAttemptFailed(n, err) is called, then retry.
  • Return anything else → the value is returned from retryWithBackoff immediately.

This lets you distinguish "no value yet, keep trying" (return undefined) from "an error happened" (throw), and log them differently.

How it works

for (let n = 1; n <= attempts; n++) {
  if (isCancelled?.()) return undefined
  try {
    const v = await attempt(n)
    if (v !== undefined) return v
  } catch (err) {
    onAttemptFailed?.(n, err)
  }
  if (n === attempts) break
  if (isCancelled?.()) return undefined
  await sleep(delay)
  if (isCancelled?.()) return undefined
  delay = Math.min(delay * 2, maxDelay)
}
onGiveUp?.()
return undefined

Walk through the steps:

  1. Cancellation check before the attempt. If the operation was cancelled since the last iteration, bail without doing work.
  2. Run the attempt. If it returns a defined value, return it. If it returns undefined, fall through to retry. If it throws, log via onAttemptFailed and fall through to retry.
  3. If this was the last attempt, break. No point checking cancellation or sleeping.
  4. Cancellation check after the attempt. If the caller cancelled while we were awaiting, bail.
  5. Sleep for delay ms. Then check cancellation again — the cancellation may have happened during the sleep.
  6. Double the delay, capped at maxDelay.
  7. After the loop, call onGiveUp and return undefined.

The three cancellation checks — before the attempt, before the sleep, and after the sleep — are the reason this is safe for React. An unmount during any part of the cycle stops the loop on the next check.

Why three cancellation checks

Each await is a potential pause. Between any two checks, the caller can set the cancelled flag. The boundaries that matter:

  • Before the attempt: don't start work that's already been abandoned.
  • After the attempt, before the sleep: the work finished but the caller may have cancelled during it. No point sleeping if we're not going to try again.
  • After the sleep: the flag may have flipped during the sleep. Don't re-enter the loop and start another attempt.

Without all three, there's a window where the operation would do extra work after cancellation. With all three, cancellation is honored at every meaningful pause.

Delay schedule

With defaults baseDelayMs = 1000, maxDelayMs = 12000, attempts = 4:

Attempt Fails → sleep Cumulative wait
1 1000ms 1s
2 2000ms 3s
3 4000ms 7s
4 — (last attempt) 7s total

With attempts = 10, delays go 1s, 2s, 4s, 8s, 12s, 12s, 12s, 12s, 12s — capped at maxDelayMs.

The cap is what Math.min(delay * 2, maxDelay) does. Without it, attempts = 20 would produce a final delay measured in days.

undefined vs thrown error

Two different failure signals, treated differently:

  • attempt returns undefined → silent retry. No onAttemptFailed call. Useful for "not ready yet, keep polling."
  • attempt throws → onAttemptFailed(n, err) is called, then retry. Useful for "something went wrong, log it and try again."

You can mix both in a single attempt:

attempt: async (n) => {
  const res = await fetch(url)
  if (!res.ok) throw new Error(`HTTP ${res.status}`)   // logged
  const data = await res.json()
  return data.ready ? data : undefined                 // silent retry
}

Both paths lead to retry. The difference is only whether the failure is logged.

Common patterns

Polling until a value is ready

const job = await retryWithBackoff({
  attempts: 20,
  baseDelayMs: 500,
  maxDelayMs: 5000,
  attempt: async () => {
    const status = await getJobStatus(id)
    return status.done ? status.result : undefined
  },
})

Effect-scoped fetch with unmount safety

useEffect(() => {
  let cancelled = false
  retryWithBackoff({
    isCancelled: () => cancelled,
    attempt: async () => fetchProfile(userId),
  }).then(p => { if (!cancelled) setProfile(p) })
  return () => { cancelled = true }
}, [userId])

Custom failure logging

await retryWithBackoff({
  attempt: () => postWebhook(payload),
  onAttemptFailed: (n, e) => log.warn({ attempt: n, err: e }, "webhook failed"),
  onGiveUp: () => log.error("webhook gave up"),
})

Silencing the default console logs

await retryWithBackoff({
  attempt: () => work(),
  onAttemptFailed: () => {},   // silence
  onGiveUp: () => {},          // silence
})

Subclass of retry logic that inspects the final error

The function doesn't return the final error. If you need it, capture it in a closure:

let lastErr: unknown
await retryWithBackoff({
  attempt: () => work(),
  onAttemptFailed: (_, e) => { lastErr = e },
})
// lastErr holds the last error, if you need it

Behavior

  • First attempt runs immediately. No delay before attempt 1.
  • n starts at 1. attempt(1), attempt(2), ... through attempt(attempts).
  • Delay is between attempts only. After the last attempt, the function returns without sleeping.
  • onGiveUp runs exactly once if the loop exhausts. It doesn't run if the function returns early on success or cancellation.
  • undefined return on: total exhaustion, or cancellation. These two cases are indistinguishable from the caller's perspective — you can't tell "tried 4 times, all failed" from "cancelled on attempt 2" without extra logging.
  • maxDelay = maxDelayMs ?? Infinity. If you pass maxDelayMs = undefined, the cap is Infinity and the delay grows unbounded (subject to Number.MAX_SAFE_INTEGER for the timer).
  • isCancelled is optional. Default is () => false, so the loop never checks. Passing undefined explicitly also works — the isCancelled?.() calls are optional.
  • attempt is optional and has a default. The default just logs. Useful only as a placeholder during development.
  • onAttemptFailed and onGiveUp are optional. Defaults log to console. Pass a no-op to silence.

runWithRetry

Run an async function, retry on failure with exponential backoff. Returns the function's value on success, undefined if every attempt failed. Logs each failed attempt with a label.

const result = await runWithRetry(() => fetchRemote(), "sync")
// → the value, or undefined if all 3 attempts failed

The point: wrap a flaky operation so a transient failure doesn't propagate. Retry, back off, give up quietly.

Usage

🟢 First-time users — start here

import { runWithRetry } from "platform"

const data = await runWithRetry(() => flakyFetch(url), "fetch")
if (!data) {
  // all attempts failed
}

That's it. You're done. You now know how to use runWithRetry.

Pass a thunk and a label. If it succeeds, you get the value. If it fails, it retries up to maxAttempts times with a delay that doubles each attempt. If all attempts fail, it logs and returns undefined — it does not throw.

Defaults: 3 attempts, 1000ms base delay.

await runWithRetry(fn, "label")                         // 3 attempts, 1s, 2s backoff
await runWithRetry(fn, "label", 5)                       // 5 attempts, 1s, 2s, 4s, 8s
await runWithRetry(fn, "label", 3, 500)                  // 3 attempts, 500ms, 1s

🔵 Everyone else

Signature

async function runWithRetry(
  fn: () => any,
  label: string,
  maxAttempts = 3,
  baseDelay = 1000,
): Promise<A | undefined>
  • fn — a thunk. Called on each attempt. May be sync or async.
  • label — a string used in log messages. [TimeMachine:${label}].
  • maxAttempts — total number of attempts, including the first. Default 3.
  • baseDelay — the initial backoff delay in milliseconds. Doubles each retry. Default 1000.
  • Returns the value of fn() on success, undefined if all attempts fail.

How it works

let attempt = 0
let delay = baseDelay
while (attempt < maxAttempts) {
  try {
    return await fn()
  } catch (err) {
    attempt++
    console.log(`[TimeMachine:${label}] attempt ${attempt} failed`, err)
    if (attempt >= maxAttempts) { console.log(`[TimeMachine:${label}] all retries failed`); return }
    await new Promise(res => setTimeout(res, delay))
    delay *= 2
  }
}
  1. Loop up to maxAttempts times.
  2. Try fn(). If it returns, return the value immediately — no further attempts.
  3. On throw or rejection, increment attempt, log the failure.
  4. If we've exhausted attempts, log once more and return undefined.
  5. Otherwise sleep for delay ms and double delay for next time.

The backoff is baseDelay * 2^(attempt - 1): 1s, 2s, 4s, 8s... starting from baseDelay. A baseDelay of 500 gives 500, 1000, 2000, ....

Why exponential backoff

Immediate retries hammer a failing service. If the service is down or overloaded, retrying at full speed makes it worse and burns your own quota. Doubling the delay gives the downstream time to recover, and spreads out retry pressure across clients (assuming the initial failures weren't synchronized).

This is the standard pattern from TCP retransmission, and it's the right default for anything crossing a network or a process boundary.

Return semantics — success, failure, undefined

The function does not throw. On total failure, it returns undefined. The caller checks for the value:

const result = await runWithRetry(fn, "sync")
if (result === undefined) {
  // all attempts failed
}

This is a real design choice, and it has consequences:

  • Pro: retries are self-contained. The caller doesn't need a try block.
  • Con: undefined is ambiguous. If fn() legitimately returns undefined, the caller can't distinguish "succeeded with undefined" from "all attempts failed." The log messages are the only signal.

If you need to distinguish, either ensure fn never returns undefined, or wrap the call site to check the logs, or copy the function and re-throw on exhaustion.

Logging

Three log lines, all console.log:

  • Per failure: [TimeMachine:${label}] attempt N failed followed by the error.
  • On exhaustion: [TimeMachine:${label}] all retries failed.

The TimeMachine prefix is hardcoded. If you're vendoring, rename it or route it through your own logger. console.log is not structured; if you need to pipe these to a log aggregator, replace the calls.

Common patterns

Flaky network calls

const res = await runWithRetry(
  () => fetch(url).then(r => r.json()),
  "api.getUser",
  5,
  250,
)

await runWithRetry(() => store.put(key, value), "store.put")

  • First attempt runs immediately. No delay before the first try.
  • Delay between attempts, not after the last. If the last attempt fails, no delay; the function returns undefined right away.
  • Backoff doubles per attempt. baseDelay, 2 * baseDelay, 4 * baseDelay, ...
  • fn can be sync or async. The await fn() handles both.
  • Synchronous throws are caught. try wraps the call, so throw inside fn is treated the same as a rejection.
  • The loop is a while with an explicit attempt counter. No for loop, no forEach, no recursion. Easy to follow and to instrument.

executor

Serial task queue. Enqueue async functions; they run one at a time, in order, each waiting for the previous to settle before starting. Returns a promise for each task's own result, so callers get their value back normally.

const ex = executor()

ex.enqueue(() => fetch("/a"))   // runs first
ex.enqueue(() => fetch("/b"))   // runs after /a settles
ex.enqueue(() => fetch("/c"))   // runs after /b settles

The point: every task sees a clean world where no other task is running. No interleaving. No shared-state races between tasks. Order is guaranteed.

Usage

🟢 First-time users — start here

import { executor } from "platform"

const ex = executor()

const a = await ex.enqueue(() => doTaskA())
const b = await ex.enqueue(() => doTaskB())

That's it. You're done. You now know how to use executor.

The .enqueue(fn) call returns a promise for that task's result. fn is a thunk — pass () => something(), not something(). Tasks run one after another in the order they were enqueued. The first task starts immediately; every subsequent one waits for the previous to settle (resolve or reject).

Errors from one task do not stop the queue. The next task still runs.

🔵 Everyone else

API

function executor(): {
  enqueue<T>(fn: () => Promise<T>): Promise<T>
  readonly idle: Promise<void>
}
  • enqueue(fn) — schedules fn to run after all previously enqueued tasks have settled. Returns a promise that resolves or rejects with fn's own result.
  • idle — a promise that resolves when the queue is empty. await ex.idle waits for everything currently enqueued to finish.

How it works

The whole class is three lines of logic:

private chain: Promise<void> = Promise.resolve()

enqueue<T>(fn: () => Promise<T>): Promise<T> {
  const run = this.chain.then(fn)
  this.chain = run.then(() => undefined, () => undefined)
  return run
}

get idle(): Promise<void> { return this.chain }
  1. this.chain is a promise that represents "everything enqueued so far." It starts resolved, so the first task runs immediately.
  2. run = this.chain.then(fn) — schedule fn to run once this.chain settles. run is the task's own promise; the caller gets it back.
  3. this.chain = run.then(() => undefined, () => undefined) — replace the chain with a version of run that swallows errors. This is the important line: whether fn resolves or rejects, the chain moves on. The next task doesn't care whether this one failed.
  4. return run — the caller sees fn's actual result or rejection. The chain saw only "settled."

The asymmetry between run and this.chain is the whole design. The queue is defined by when tasks settle, not by whether they succeed. Errors are the caller's problem; the queue's job is just ordering.

Why the error-swallowing matters

Without run.then(() => undefined, () => undefined), this would happen:

// hypothetical wrong version
this.chain = run

If a task rejects, this.chain becomes a rejected promise. The next this.chain.then(fn) would skip fn and propagate the rejection — the queue would be permanently broken. Every task after the first failure would silently not run.

The real implementation catches both branches and returns undefined, so this.chain always resolves. The queue never breaks, no matter how many tasks fail.

Why "serial" matters

Concurrent async work interleaves at every await. If two tasks both read-modify-write shared state, they'll race even in a single-threaded runtime — because between one task's await a() and its await b(), another task can run. Serial execution removes the interleaving. Each task runs to completion (through all its awaits) before the next starts.

This is what you want when:

  • Tasks share mutable state that isn't safe under interleaving.
  • Tasks must observe each other's effects (task B needs to see task A's writes).
  • Order of side effects matters (network calls, file writes, event emissions).
  • You want the simplest possible concurrency model: one thing at a time.

Common patterns

Serialized writes to a shared resource

  return writer.enqueue(async () => {
    await fs.writeFile(path, serialize(doc))
    await fs.fsync(fd)
  })
}

No two writes interleave. No torn files.

Ordered network requests

Requests go out one at a time, in the order of ids.

Draining before shutdown

Rate-limited external calls

Behavior

  • FIFO order. Tasks run in enqueue order.
  • One at a time. A task starts only after the previous one settles.
  • Errors don't break the queue. A rejected task still lets the next one run.
  • Caller sees the real result. run is the promise that resolves or rejects with fn's value. The queue's internal bookkeeping never interferes with what the caller receives.
  • idle is a snapshot. It resolves when the queue as-of-now is drained. Tasks enqueued after you access idle aren't included. If you want to keep draining, re-read idle after each round.
  • First task runs immediately. this.chain starts as Promise.resolve(), so the first .enqueue schedules fn on the next microtask, not after any delay.
  • No concurrency limit beyond 1. This is a strictly serial queue, not a pool.

setKey

Set a single key on object state via a React-style setter. Always uses the functional updater, so the previous state is never read from a stale closure.

setKey(setUser, "name", "Alice")
// → setUser(prev => ({ ...prev, name: "Alice" }))

One key, one value, one call. It's the typed, single-purpose version of setPrev's key-branch.

Usage

🟢 First-time users — start here

import { setKey } from "platform"

setKey(setForm, "name", "Alice")
setKey(setForm, "age", 30)
setKey(setForm, "submitted", true)

That's it. You're done. You now know how to use setKey.

It's the same as writing setForm(prev => ({ ...prev, name: "Alice" })), but the key and value are typed against the state shape — so TypeScript catches typos in the key and wrong-typed values before you run the code.

🔵 Everyone else

Signature

function setKey<T extends object, K extends keyof T>(
  setState: any,
  key: K,
  value: T[K],
): void
  • setState — a React-style setter. Typed any here because React's Dispatch<SetStateAction<T>> doesn't compose nicely with the generic constraints, and the runtime doesn't need it.
  • key — must be a key of T.
  • value — must match the type of T[K], i.e. the type of that specific key.
  • Returns void.

The T is inferred from the setter at the call site — but since setState is any, inference falls back to T being inferred from key and value in practice. In tightly-typed codebases, you may need to annotate:

setKey<User, "name">(setUser, "name", "Alice")

or supply a typed wrapper. See gotchas.

How it works

setState((prev: any) => ({ ...prev, [key]: value }))

One line. It builds the functional updater and hands it to the setter. prev is whatever the latest state is when React applies the update — never a captured value from the render closure.

The result is a shallow clone of prev with one key replaced. Nested objects are shared by reference, which is exactly what you want for a state update.

The point of the types

The value of setKey over just writing setState(prev => ({ ...prev, [key]: value })) inline is the type signature:

  • key: K extends keyof T — the key must exist on the state type. Typo a key and the compiler complains.
  • value: T[K] — the value must match the type at that key. Assign a string to a numeric field and the compiler complains.

Neither check is enforced at runtime — the helper does the same thing regardless. But the editor catches errors before you hit save.

Common patterns

Controlled inputs

<input
  value={form.name}
  onChange={e => setKey(setForm, "name", e.target.value)}
/>

Clearing a single field

Setting a boolean flag

setKey(setUi, "loading", true)

Factory for field handlers

  (value: Form[K]) => setKey(setForm, key, value)

const setName = bind("name")
const setAge = bind("age")

Behavior

  • Shallow clone. { ...prev, [key]: value } creates a new object at the top level. Nested objects are the same references as before.
  • Functional updater. Always reads the latest prev. Safe to call multiple times in the same tick, safe after an await.
  • Never mutates prev. A fresh object is handed to the setter.
  • Key stays present even when value is undefined. setKey(setForm, "error", undefined) produces { ...prev, error: undefined } — the key exists with an undefined value. This matters for Object.keys and iterating over the object.

Differences from setPrev

setPrev does two things:

  1. Single-key update with k provided.
  2. Object merge when k is omitted.

setKey does only the first, with the key and value properly typed against the state shape. If you're reaching for setPrev with a key every time, use setKey instead — you get the same behavior with better types and a clearer name.

Use setPrev when you're doing a merge (no key). Use setKey when you're setting exactly one field.

setPrev / setPrevB

Functional state setters for React-style useState. Give them a setter, give them a value, and they update based on the previous state without you having to write setX(prev => …) inline every time.

setPrev(setUser, "name", "Alice")   // setUser(prev => ({ ...prev, name: "Alice" }))
setPrev(setUser, { age: 30 })       // setUser(prev => ({ ...prev, age: 30 }))
setPrevB(setOpen)                   // setOpen(prev => !prev)

Two shapes: setPrev for object state with a single key or a merge, setPrevB for boolean toggles.

Usage

🟢 First-time users — start here

import { setPrev, setPrevB } from "platform"

// Toggle a boolean
setPrevB(setOpen)

// Set one key on an object
setPrev(setForm, "name", "Alice")

// Merge several keys
setPrev(setForm, { name: "Alice", age: 30 })

That's it. You're done. You now know how to use both.

They exist because setState(prev => ({ ...prev, key: value })) is the same boilerplate every time, and the form with the spread is where people accidentally write setState({ ...state, ... }) and use a stale state. These helpers force the functional form, so you can't reference stale state by accident.

🔵 Everyone else

Signatures

function setPrev<T = any>(setter: any, k?: any, v?: any): void
function setPrevB(setter: any): void
  • setter — a React-style state setter (Dispatch<SetStateAction<S>>).
  • v — the value to set. With k provided, this is the value for that key. Without k, this is an object to spread-merge into prev.
  • k — optional key. If provided, only that key is updated.
  • setPrevB toggles a boolean via !prev.

Both return void. They call the setter with a functional updater and don't return anything.

What setPrev does

setPrev(setter, k?, v)

Two modes, chosen by whether k is undefined:

With k — single-key update:

setter((prev) => ({ ...prev, [k]: v }))

Clone the previous object, replace one key, hand the clone to the setter. The prev is never mutated.

Without k — object merge:

setter((prev) => ({ ...prev, ...(v as Partial<any>) }))

Clone the previous object, spread the new object over it, hand the clone to the setter. Useful for multi-field updates:

setPrev(setForm, { name: "Alice", age: 30 })

Both modes rely on prev being an object. If prev is a primitive, the spread produces a weird result — see gotchas.

What setPrevB does

setter((prev) => !prev)

Toggles. true becomes false, everything truthy becomes false, everything falsy becomes true. Named B for boolean, but the implementation is a plain logical-not, so it works on any value with a boolean interpretation. The common case is a useState<boolean>.

Why the functional form matters

The bug setPrev prevents is subtle:

// ❌ uses `state` from the render closure — stale if the setter is called
//    twice in the same tick, or after an async boundary
setUser({ ...user, name: "Alice" })

// ✅ uses the latest state, always
setUser(prev => ({ ...prev, name: "Alice" }))

The functional form is correct. The direct-object form is a footgun that works in tests and breaks in production. setPrev and setPrevB make the correct form the only form. You can't accidentally reach for stale state because the helper never gives you a way to.

Common patterns

Controlled form fields

<input onChange={e => setPrev(setForm, "name", e.target.value)} />
<input onChange={e => setPrev(setForm, "email", e.target.value)} />

Multi-field updates

Toggle UI state

<button onClick={() => setPrevB(setOpen)}>Toggle</button>
<button onClick={() => setPrevB(setLoading)}>Loading</button>

Reset a field

Clear a form

Behavioral notes

  • Never mutates prev. Both modes spread into a new object. The setter receives a fresh reference.
  • Synchronous call to the setter. The helper builds the functional updater and calls it. React schedules the actual state update.
  • Idempotent within a tick. Calling setPrev(setter, "a", "x") twice in the same render queues two updaters, each applied to the result of the previous. Both are correct.
  • prev is captured by the closure. The updater reads prev at the moment React invokes it, not at the moment the helper was called. That's the whole point.

sleep

Wait for a number of milliseconds. Returns a promise that resolves after the delay. That's the whole thing.

await sleep(1000)   // waits one second

The point: an awaitable delay. setTimeout is a callback API; sleep is the promise version. Pause an async function without wrapping setTimeout in a promise every time.

Usage

🟢 First-time users — start here

import { sleep } from "platform"

await sleep(1000)

That's it. You're done. You now know how to use sleep.

Pause, then continue. sleep(0) yields to the next macrotask — useful for "let the event loop breathe" moments.

🔵 Everyone else

Signature

const sleep = (ms: number): Promise<void>
  • ms — milliseconds to wait. Standard setTimeout semantics apply.
  • Returns Promise<void> — resolves with undefined after the delay.
  • Never rejects. No cancellation. No signal.

How it works

new Promise(resolve => setTimeout(resolve, ms))

One line. setTimeout is called with resolve as the callback, so the promise settles when the timer fires. The value passed to resolve is undefined (the return value of setTimeout's callback is discarded).

Timing semantics

sleep(ms) does not guarantee "resume after exactly ms milliseconds." It guarantees "resume no earlier than ms milliseconds from now, whenever the event loop gets around to it." Three things can push the actual resume later:

  1. The event loop is busy. If a long synchronous task is running when the timer fires, sleep resumes after that task finishes.
  2. Other timers are queued ahead. setTimeout callbacks fire in order of scheduled time, but if the loop is behind, they all run together.
  3. Browsers clamp timers. Nested timers beyond 5 levels are clamped to a minimum of 4ms. Background tabs clamp to 1000ms or more. This is the platform, not sleep.

For most code, none of this matters. If you're building a precise timer, use performance.now() and re-schedule.

sleep(0) — yielding

sleep(0) doesn't "sleep." It schedules a macrotask via setTimeout(_, 0). This yields control back to the event loop, allowing pending microtasks and I/O callbacks to run before resuming. Useful when you want to break up a synchronous loop:

for (const item of hugeList) {
  process(item)
  await sleep(0)   // let the event loop breathe
}

This is the macrotask equivalent of await Promise.resolve(). It's slower than a microtask yield but allows I/O to run in between.

Common patterns

Basic pause

await sleep(500)

Rate limiting in a loop

for (const item of items) {
  await process(item)
  await sleep(100)   // 100ms between items
}

Backoff between retries

for (let i = 0; i < 5; i++) {
  try { return await attempt() }
  catch { await sleep(1000 * 2 ** i) }
}

Same pattern as runWithRetry and retryWithBackoff, written out inline.

Yield to the event loop

await sleep(0)

Minimal debounce

let pending: Promise<void> | undefined
function debounced() {
  pending = sleep(100).then(run)
}

Not the real debounce pattern, but sleep is the delay primitive underneath.

Composing with a timeout

await Promise.race([operation(), sleep(5000).then(() => { throw new Error("timeout") })])

sleep is the timeout arm of a race. The same trick appears inside timedPromise.

Behavior

  • Always resolves with undefined. Never with a value, never rejects.

  • Timers aren't cancelled by anything. Once sleep is called, the timer runs even if the caller's outer context has given up. The promise will resolve; whether anyone is still awaiting it is another matter.

  • No AbortSignal support. No way to cancel from outside. If you need cancellable sleep, wrap it:

    function cancellableSleep(ms: number, signal: AbortSignal) {
  return new Promise<void>((resolve, reject) => {
    const timer = setTimeout(resolve, ms)
    signal.addEventListener("abort", () => {
      clearTimeout(timer)
      reject(new Error("aborted"))
    }, { once: true })
  })
}

    sleep deliberately doesn't do this. It's the smallest possible delay primitive.

  • ms can be negative or NaN. setTimeout coerces to 0. sleep(-100) is effectively sleep(0).

  • ms can be Infinity. setTimeout(_, Infinity) is treated as setTimeout(_, 0) in most engines — it doesn't wait forever. If you need "never resolve," use new Promise(() => {}).

timedPromise

Race a promise against a timeout. If the promise settles first, you get its result. If the timeout fires first, you get a rejection with a clear message. The timer is always cleared, so a fast resolve doesn't leave a dangling setTimeout keeping the process alive.

await timedPromise(fetchUser(id), 5000)
// → resolves with the user, or rejects with "[rift] wait() timed out after 5000ms"

Usage

🟢 First-time users — start here

import { timedPromise } from "platform"

const user = await timedPromise(fetchUser(id), 5000)

That's it. You're done. You now know how to use timedPromise.

It's await on the promise, except if it takes longer than timeoutMs, you get a rejection instead of waiting forever. The rejection is a regular Error — catch it like any other.

try {
  const user = await timedPromise(fetchUser(id), 5000)
} catch (e) {
  // either fetchUser rejected, or it took longer than 5s
}

🔵 Everyone else

Signature

function timedPromise<T>(gate: Promise<T>, timeoutMs: number): Promise<T>
  • gate — the promise you actually care about.
  • timeoutMs — how long to wait, in milliseconds.
  • Returns a Promise<T> that resolves with gate's value, rejects with gate's rejection, or rejects with a timeout error if timeoutMs elapses first.

How it works

let timer!: ReturnType<typeof setTimeout>
const timeout = new Promise<T>((_, reject) => {
  timer = setTimeout(() => reject(new Error(`[rift] wait() timed out after ${timeoutMs}ms`)), timeoutMs)
})
return Promise.race([gate, timeout]).finally(() => clearTimeout(timer))

Three parts:

  1. A timeout promise is created that rejects after timeoutMs. The timer handle is captured in timer so it can be cleared later.
  2. Promise.race resolves or rejects with whichever of gate or timeout settles first.
  3. .finally clears the timer regardless of which side won — so a fast gate resolve doesn't leave a stray setTimeout on the event loop.

The ! on timer is a TypeScript assertion: the executor runs synchronously, so by the time the line timer = setTimeout(...) finishes, the assignment has happened. There is no window where timer is uninitialized when .finally runs.

Why the timer is cleared

A setTimeout that hasn't fired yet is a live event-loop handle. If you don't clear it, a process that calls timedPromise many times will accumulate pending timers, and a Node process with pending timers won't exit on its own. The .finally guarantees the cleanup fires on both branches:

  • Gate wins → .finally runs → timer cleared → no pending handle.
  • Timeout wins → .finally runs → timer cleared (already fired, so clearing is a no-op, but it's harmless and correct).

Clearing a fired timer is safe in Node and in browsers. So this works uniformly without a branch.

Behavior

  • Fast resolve → T, timer cleared, no rejection.
  • Fast reject → gate's rejection, timer cleared.
  • Slow resolve → Error("[rift] wait() timed out after Nms") after timeoutMs.
  • Slow reject → the timeout error wins the race; gate's eventual rejection is swallowed by Promise.race.
  • timeoutMs: 0 → the timeout fires on the next tick. Usually the gate loses. Rarely useful, occasionally useful for "must already be resolved."
  • Negative or NaN timeoutMs → setTimeout coerces to 0. Same as above.

Common patterns

Bounding an unreliable call

const response = await timedPromise(fetch(url), 10_000)

Bounding an internal operation

const result = await timedPromise(runJob(job), 30_000)

Composing with retry

for (let i = 0; i < 3; i++) {
  try {
    return await timedPromise(fetchUser(id), 2_000)
  } catch (e) {
    if (i === 2) throw e
  }
}

Detecting a timeout specifically

The rejection is a plain Error with a recognizable message prefix ([rift]). If you need to distinguish timeouts from real failures, check the message, or wrap the whole thing:

try {
  return await timedPromise(gate, ms)
} catch (e) {
  if (e instanceof Error && e.message.startsWith("[rift] wait()")) {
    // it timed out
  }
  throw e
}

toPromise

Lift any value into a Promise. Same behavior as Promise.resolve, but with a name that says what the call site means: "turn this into a promise."

toPromise(42)          // Promise<42>
toPromise(fetchUser()) // passes the promise through
toPromise(undefined)   // Promise<undefined>

Usage

🟢 First-time users — start here

const p = toPromise(maybeValueOrPromise)
const v = await p

That's it. You're done. You now know how to use toPromise.

Whatever you give it — a number, a string, an object, an existing promise — you get a promise back. await it and you get the original value. If you passed a promise, it isn't double-wrapped; it passes through.

🔵 Everyone else

Signature

const toPromise = <T>(value: T | PromiseLike<T>): Promise<T>
  • Accepts a plain T or anything promise-like (PromiseLike<T> — anything with a .then).
  • Returns Promise<T>.
  • Delegates directly to Promise.resolve(value).

That last line is the whole implementation. toPromise is Promise.resolve with a different name.

Why it exists

Promise.resolve has a name that's about promises. toPromise has a name that's about conversion. The two are the same operation, but they read differently at a call site:

// "resolve this promise"
Promise.resolve(x)

// "convert this value to a promise"
toPromise(x)

When you're writing a function that accepts T | Promise<T> and need to guarantee a Promise<T> out the other side, toPromise(x) documents why you're calling it. Promise.resolve(x) works identically but leaves the reader to guess the intent.

Behavior

  • Plain value → wrapped in a resolved Promise<T>.
  • Promise → passed through as-is (not re-wrapped).
  • Thenable (non-Promise object with .then) → adopted; the result of Promise.resolve on a thenable is a real Promise<T> that follows the thenable's behavior.
  • Promise subclass → returns a real Promise, not the subclass. (Standard Promise.resolve semantics.)
  • undefined and null → both produce resolved promises. toPromise(undefined) is Promise<undefined>. Unlike MaybePromise, there's no special-casing.

Common patterns

Function that returns either sync or async

function get(id: string): Promise<User> {
  const cached = cache.get(id)
  if (cached) return toPromise(cached)   // sync hit, promoted to promise
  return fetchUser(id)                   // async miss
}

Normalizing input

function handle(input: T | Promise<T>) {
  return toPromise(input).then(process)
}

Forcing a promise boundary

const results = await Promise.all(items.map(toPromise))

Adapting a thenable

const p = toPromise(customThenable)
// p is a real Promise, not the thenable

toPromise vs MaybePromise

Different jobs, same neighborhood:

  • toPromise(x) — always returns Promise<T>. Wrap unconditionally. Use when the caller needs a promise.
  • MaybePromise(x) — returns x unless x is undefined, in which case it returns a resolved promise. Use when you want to skip the promise when the value is already there.

toPromise is the honest, always-async version. MaybePromise is the chameleon that preserves sync identity when it can.

tryCatch

Run a function, get back a tuple. Either [undefined, value] on success or [error, undefined] on failure. No thrown exceptions escape. Ever.

const [err, user] = await tryCatch(() => fetchUser(id))

if (err) {
  // handle the error
} else {
  // user is T
}

The point: turn the try / catch statement into a value you can pass around, store, branch on, or return. Errors become data instead of control flow.

Usage

🟢 First-time users — start here

import { tryCatch } from "platform"

const [err, data] = await tryCatch(() => riskyOperation())

if (err) {
  console.error(err)
} else {
  console.log(data)
}

That's it. You're done. You now know how to use tryCatch.

The rule is one sentence: one side of the tuple is always undefined. If the call succeeded, err is undefined and data holds the value. If it failed, data is undefined and err holds the Error. You check one, you know the other.

It always returns a Promise — even if fn is synchronous — so the call site is await in both cases.

🔵 Everyone else

Signature

async function tryCatch<T>(
  fn: () => T | Promise<T>
): Promise<[Error, undefined] | [undefined, T]>
  • fn — a zero-argument function. May be sync or async. May throw or reject.
  • Returns a Promise that always resolves. Never rejects.
  • The tuple is discriminated by which slot is undefined: [Error, undefined] on failure, [undefined, T] on success.

TypeScript narrows automatically on the if (err) check, so inside the else branch data is typed T — no cast needed.

How it works

try { return [undefined, await fn()] }
catch (e) { return [e instanceof Error ? e : new Error(String(e)), undefined] }
  • fn() is invoked inside a try. The result is awaited.
  • On success, [undefined, value] is returned.
  • On throw (sync or async), the error is caught, coerced to an Error if necessary, and returned as [error, undefined].

Because the function is async, both return paths produce a resolved promise. The caller can't get an unhandled rejection out of this — the only ways to get a rejection would be for the tuple construction itself to throw, which it doesn't.

The two-tuple shape

The [error, value] order follows the Go and Node convention (and the original await-to-js style). Error first, value second. The asymmetry — one slot is undefined when the other is populated — is what makes narrowing work in TypeScript:

const [err, v] = await tryCatch(fn)
if (err) {
  // v is undefined
} else {
  // v is T
}

If both were always T | undefined, you'd have to assert. The tuple union gives you discrimination for free.

Error coercion

e instanceof Error ? e : new Error(String(e))

If fn throws an Error, you get it back untouched. If fn throws a string, a number, null, or anything else, it's wrapped in a fresh Error with String(e) as the message. The contract is: the first slot is always an Error, never a raw throw value.

This matters because throw "oops" and throw { code: 42 } are legal in JS. Callers shouldn't have to defensively check. tryCatch normalizes.

Common patterns

Error-first call sites without a try block

const [err, config] = await tryCatch(() => loadConfig(path))
if (err) return defaultConfig
return config

Collecting results from a batch

const results = await Promise.all(
  items.map(i => tryCatch(() => process(i)))

unreachable

A never-returning function for exhaustiveness checks. Call it in the default branch of a discriminated union switch, and TypeScript will fail compilation if a case is ever added without being handled.

type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; s: number }

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle": return Math.PI * shape.r ** 2
    case "square": return shape.s ** 2
    default: return unreachable(shape)
  }
}

Add a triangle variant and the default branch stops compiling — because shape is no longer never there.

Usage

🟢 First-time users — start here

import { unreachable } from "platform"

function label(status: "ok" | "warn" | "error"): string {
  switch (status) {
    case "ok": return "fine"
    case "warn": return "check"
    case "error": return "broken"
    default: return unreachable(status)
  }
}

That's it. You're done. You now know how to use unreachable.

Put it in the default: of every switch over a union. It compiles today. When someone adds a new variant to the union, the compiler tells them they missed a case. If somehow the code runs anyway (dynamic input, bad types, any leaking in), it throws with the offending value in the message.

🔵 Everyone else

Signature

const unreachable = (value: never): never
  • Parameter is typed never — the type system's bottom type. Only values the compiler considers impossible can be passed.
  • Return type is never — the function never returns normally. It throws.

The two nevers do different jobs. The parameter never is what makes this an exhaustiveness check: it can only be satisfied when the compiler has nothing left. The return never is what makes the default: branch typecheck against a function that's declared to return number — a function that never returns is assignable anywhere.

Why it's a compile-time tool first

The runtime behavior is trivial — throw with a helpful message. The value is in the type:

type E = "a" | "b"

function f(e: E) {
  if (e === "a") return 1
  if (e === "b") return 2
  return unreachable(e)   // e: never — OK
}

Now add "c" to E:

type E = "a" | "b" | "c"

The unreachable(e) call fails to compile:

Argument of type 'string' is not assignable to parameter of type 'never'.

The compiler catches the missing case before the code runs. That's the whole reason this function exists.

Why it also throws at runtime

Types don't enforce reality at runtime. Data comes from JSON, from the network, from any-typed boundaries, from old versions of the app talking to new versions of the server. If a value that the types said couldn't happen shows up anyway, the function throws with the actual value in the message:

Unreachable value: "triangle"

That's a test failure, a crash, a logged incident — something that surfaces immediately instead of silently returning undefined or falling through to a wrong branch. Fast, loud failure over quiet corruption.

Behavior

  • Always throws. Always. No return path.
  • Message includes the value. Unreachable value: ${String(value)}. For objects, String({}) is "[object Object]", so you won't see the shape — serialize explicitly if you need that.
  • Throws a plain Error. Not a custom class. If you want a typed UnreachableError, wrap it.
  • Return type is never. Assignable to any function's return type. Safe in expressions.

wait_and_promise

Subscribe to a key, then check whether the condition is already true. If it is, resolve immediately with the current value. If not, wait for the subscription to fire. If neither happens before timeoutMs, reject.

The ordering — subscribe first, then re-check — is the entire point. It closes the race window where the thing you're waiting for fires between your early-return check and your subscription.

const value = await wait_and_promise(5000, key, isOpen(), currentValue)
// → resolves with next.value when the subscription fires with opened: true
// → resolves immediately with currentValue if isOpen was already true
// → rejects after 5000ms if neither happened

Usage

🟢 First-time users — start here

import { wait_and_promise } from "platform"

const value = await wait_and_promise(
  5000,           // timeout in ms (0 or falsy = no timeout)
  myKey,          // subscription key
  isOpen(),       // is the thing already open right now?
  currentValue,   // value to resolve with if it's already open
)

That's it. You're done. You now know how to use wait_and_promise.

Three possible outcomes:

  1. It's already open → resolves immediately with currentValue.
  2. It opens while you're waiting → resolves with the new value.
  3. It never opens → rejects after timeoutMs with a timeout error.

Pass 0 (or any falsy value) as timeoutMs to wait forever with no timeout.

🔵 Everyone else

Signature

function wait_and_promise<T = A>(
  timeoutMs: number,
  key: A,
  isOpen: A,
  current: A,
): Promise<T>
  • timeoutMs — milliseconds before rejection. 0 or falsy disables the timeout entirely.
  • key — the subscription key passed to sub.
  • isOpen — a truthy value if the condition is already satisfied. Checked after subscribing.
  • current — the value to resolve with if isOpen is truthy.
  • Returns Promise<T>.

Why subscribe before checking

The naive version is:

if (isOpen) return current          // check
const unsub = sub(key, handler)     // then subscribe

The gap between those two lines is a race. If the condition flips to open between the check and the subscribe, the subscription never sees the transition (because it happened before the subscription existed), and the check already returned false. The caller hangs until timeout even though the condition was true.

The correct order is the opposite:

const unsub = sub(key, handler)     // subscribe first
if (isOpen) { unsub(); resolve(current); return }   // then check

Now the two cases are:

  1. Condition was already open before subscribe → the check catches it. Resolve with current.
  2. Condition opens after subscribe → the handler catches it. Resolve with next.value.

There is no third case where the transition happens between the check and the subscribe, because the subscribe already happened. The handler fires, the check is redundant but harmless, and the promise settles.

The cost of this correctness is one line: the if (timer) clearTimeout(timer) and unsub() must run on both paths, so the subscription is never leaked.

How it works, line by line

return new Promise<T>((resolve, reject) => {
  let timer: ReturnType<typeof setTimeout> | undefined;

  const unsub = sub(key, (next) => {
    if (next?.opened) {
      if (timer) clearTimeout(timer);
      unsub();
      resolve(next.value as T);
    }
  });

  if (isOpen) {
    if (timer) clearTimeout(timer);
    unsub();
    resolve(current as T);
    return;
  }

  if (timeoutMs) {
    timer = setTimeout(() => {
      unsub();
      reject(new Error(`[rift] wait() timed out after ${timeoutMs}ms`));
    }, timeoutMs);
  }
});
  1. sub(key, handler) registers the subscription. The handler is called whenever the value at key changes.
  2. Handler checks next?.opened. If truthy, it clears the timer (if one exists), unsubscribes, and resolves with next.value. The next?. optional chain guards against a null / undefined payload.
  3. if (isOpen) — after subscribing, check whether the condition is already satisfied. If so, clear timer, unsubscribe, resolve with current. The return prevents falling through to the timer setup.
  4. if (timeoutMs) — only arm a timer if a timeout was requested. 0 (or any falsy value) means "wait forever." The timer callback unsubscribes and rejects.

Order of cleanup on every exit path: clear the timer first (if set), then unsubscribe, then resolve or reject. Clearing the timer before unsubscribing is not strictly required, but it prevents the timer callback from running unsub() a second time if there's any interleaving.

Two ways to resolve, one way to reject

The promise resolves through exactly two channels:

  • The subscription handler — next.value when the subscription fires with opened: true.
  • The immediate check — current when isOpen is truthy at subscribe time.

It rejects through exactly one:

  • The timer — when timeoutMs elapses without either resolve path firing.

resolve and reject are idempotent in JavaScript — the first call wins, subsequent calls are no-ops. So even if the handler fires and the timer would have fired and the check runs, only the first resolve or reject has any effect. The explicit cleanup exists to prevent leaks, not to prevent double-settling.

The race this closes

Imagine the state flips from closed to open exactly once, in this timeline:

t0: caller checks isOpen → false
t1: state flips to open (fires subscription handlers)
t2: caller subscribes

Naive version: isOpen check at t0 was false, subscribe at t2 missed the transition. Caller waits forever (or until timeout).

This version:

t0: caller subscribes
t1: state flips to open → handler fires → resolve
t2: (unreachable — promise is settled)

Or:

t0: caller subscribes
t1: caller checks isOpen → true (state already flipped before t0)
t2: resolve immediately

Both cases resolve. Neither hangs.

The tradeoff is that isOpen and current must be captured before the call — they're arguments, not re-read inside the promise. If the state changes between the caller's isOpen() and the sub() inside wait_and_promise, the immediate check might be stale. But the subscription will still fire if the state changes again, and if the state is already open at check time, current is what the caller passed. The contract is: isOpen and current should be read from the same source at the same moment.
